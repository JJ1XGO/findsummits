# Lessons Learned

> 未解決バグ・課題は `mgmt/tracker/` で管理（二重管理しない）。
>
> **記述規約**: 新規エントリは「〜する」の処方形で書く（「〜してはならない」形は使わない）。重要度が高い場合は【重大】を付けてよいが、内容は肯定形を維持する。

## アルゴリズム・実装

- **初期化済み領域への上書きリセットは行わない**: `calloc` で初期化済みの場合、再ゼロリセットは不要。コードを書く前に「本当に必要か」を確認する。（commit: 13b1f72）
- **Union-Find の `union` 時は海面コンポーネントを確認する**: `peak_id < 0` の海面コンポーネントとの接触を見落とすと「コル」として誤検出する。（commit: c317186）
- **フラグ命名は肯定形・並列一貫性の両方を考慮する**: 真偽値フラグは否定形より肯定形（true=正常）を優先し、並列フラグ群全体で方向を揃える。単独の読みやすさだけで決めると並列性が崩れる。（2026-05-19）

## 設計判断

- **運用ミス起因の異常はフェイルファースト**: prefetch 漏れ等、解析対象メッシュにタイルが1枚もない場合はスキップ続行ではなく処理を中止し、原因調査と再実行をユーザーに促す。（2026-06-12: ISSUE-089 FR-004 異常系の書き換えで確認）

- **フリンジピーク除外はピーク出力段階（CSV 出力ループ）で行う**: combined 画像の端タイルはタイル座標の `floor()` 丸め誤差で地理境界より ~17px（~80m）外側にはみ出す。フリンジデータはコル検出に必要なため削除不可。Python（merge.py）側でフィルタすると analysis_count / expected_count ロジックへの影響が生じるため C 側で完結させる。（2026-05-02・BUG-014）

- **DEM1a は不採用**: プロミネンス 150m 判定には DEM5（5m解像度）で十分。DEM1a はデータ量が 25 倍になるが精度向上はほぼない。

- **レベル15→14ダウンサンプリングはmax pooling採用**: プロミネンス計算目的では山頂を保持するmax poolingが適切。キーコルは実際より高く評価されプロミネンスが過小になるが、申請に対して保守的な方向なので許容範囲。NODATAは最大値計算から除外すること。
  - **用途**: 大山・東北の独立峰など、解析範囲内でKeyコルが見つからないピークに対して広域再解析する手段として。
  - **実装方針**: タイルファイルを作るのではなく、レベル15タイルを読み込んで結合する際にmax poolingでレベル14化する。同じメモリで4倍の面積をカバーできる。

- **dem10b が存在しないタイルがある（GSI側未整備）**: prefetch しても一部タイルが取得できないのは GSI 側が HTTP 404 を返すため（取得漏れではない）。欠損は南部メッシュ（35.7°N以南）に集中。Cコードは NODATA(-9999) 扱いで解析続行するため動作上の問題なし。terrain PNG での矩形ブロック状の異常はこれが原因。

## プロセス

- **バージョン管理は `.gitignore` に一本化し `git add -A` で運用する**: 機密ファイルの誤コミット防止は `.gitignore` で完結させる。個別ファイル指定は手動列挙漏れのリスクがある。`git status` で想定外の野良ファイルがないことを目視確認のうえ `git add -A`。（2026-06-18）

- **欠陥管理フローの順序を守る**: 発見 → 登録 → 承認 → `対応中` に更新 → 実装 → `make` → `対応完了`（bug close） → ユーザー verify → `解決済`（bug verify）。`bug close` の前に必ず `bug update --status 対応中` が必要。

- **plan.md を常に最新に保つ**: 実装変更・設計変更があった場合は todo.md だけでなく plan.md も必ず更新する。plan.md が古くなると「設計と実装の乖離」が生じ、次セッション以降の判断が狂う。

- **PyMarkdown の front-matter 拡張を有効にする**: YAML frontmatter（`---`）付きの .md を lint するときは `.pymarkdown` に `extensions.front-matter.enabled: true` を足す。これがないと終端の `---` が setext 見出しの下線と誤読され MD041/MD003/MD022 が誤検出される。lint が想定外エラーを出したらまず設定（拡張の有効/無効）を疑う。（2026-06-25）

- **`mgmt/plan.md` 内のファイル参照はコード表記にする**: 計画内のリポジトリ内ファイル参照を Markdown リンクにしない。`mv` 前後どちらの起点でも相対リンクは壊れるため、コード表記（バッククォート）で書けば構造的に回避できる。`mgmt/plan.md` は lint 対象に残したまま（隠さない）。

- **【重大】Sonnet 推奨後はユーザーが切り替えるまで実装ファイルを触らない**: ExitPlanMode 承認後に Sonnet 切替を促した場合、同一レスポンス内で実装ファイル（`.c/.h/.py`）を編集しない。Opus 継続が正当な場合は推奨せず最初から「Opus 継続」を理由付きで申し出る。PreToolUse hook による機械的ゲートを `/workspace/.claude/settings.local.json` に設置済み（2026-06-25）。

- **【重大】仕様変更は実装前にユーザーと合意を取る**: ユーザーと合意した仕様を技術的困難を理由に変更する場合も、必ず状況を説明して合意を得てから行う。

- **【重大】書き込み先が許可済みか事前確認する**: `dangerouslyDisableSandbox: true` が要求されるコマンドは実行しない。書き込もうとしたパスが許可されていない場合は、ユーザーに説明して許可を得る。

- **【重大】明示されたスコープの境界で止まる**: 「〜まで」「〜だけ」と範囲が明示された指示は、その境界で必ず止まる。次のステップが明らかであっても、ユーザーの明示的な指示なしに先へ進まない。（2026-04-24）

- **【重大】テスト・解析実行前にユーザー確認を取る**: このプロジェクトはデータ量が多くテスト1回の待ち時間が長い。複数の修正をまとめてからテストしたいため、実行前に必ず確認する。疑問形のメッセージ（「〜してない？」等）は確認であり実行指示ではない。（2026-04-26）

- **【重大】引き継ぎ資料は構造的含意まで読み取る**: handover・plan.md・ADR の「次にやること」を完全に吸収してから設計判断・実装を開始する。見出しの言葉（例:「per-mesh エンジン流用」）が示すループ構造・既存 FR の再利用まで読み取ること。（2026-05-18）

- **ユーザー発言の配置意図と実装方式意図を分けて確認する**: 「フェーズ2 に位置付けたかった」「per-mesh で扱いたい」のような発言は、SRS 上の配置選好だけでなく既存エンジンの流用・拡張という実装方式の含意を含むことが多い。両方の意図を確認してから設計する。（2026-05-18）

- **既存提案への部分修正発言は「追加か置換か」を明示確認する**: 複数キーのソート順など構造的提案に対してユーザーが部分修正を示した場合、明示されていない残りのキーの扱いを確認する。（2026-05-20）

- **issue 判定は「残作業の性質」で行う（出自ではない）**: レビュー由来タスクでも、残作業がコメント修正・命名追従・機械的変換だけなら `todo.md` が正しい。複数件をまとめて登録するときも 1 件ずつ判定すること。（2026-06-08）

- **spec-panel の指摘は SRS 本文を照合してから適用する**: spec-findings は対応済み/未対応の正本ではなくレビュー時点のスナップショット。指摘を修正に適用する前に、必ず SRS 本文の対象箇所を Read で開いて目視確認する。「指摘がある ≠ 未対応」。（2026-06-30）

## 設計・仕様

- **出力列には単一の概念のみを入れる**: 「突合結果」（matched/new/deleted）と「解析品質」（confirmed/unstable）のような複数概念を1列に混在させない。概念ごとに列を分ける（match_status / stability）。

- **調整可能なパラメータは最初から設定ファイルで管理する**: `tolerance_px` のように「結果を見て調整したい」パラメータは、最初から設定ファイル（fetch_config.ini）に入れておく。コマンドライン引数のデフォルト値として直接書くと後から移行コストが発生する。

- **ソースコード付属データはプロジェクトルートからの相対パスで参照する**: `DATA_DIR`（環境依存）配下にソースコード付属のデータを置かない。`Path(__file__).parent.parent` でプロジェクトルートを参照する。ただし geojson_v{N}・summitslist.csv は「ユーザーが手動配置する入力」として §7 ユーザー入力に再分類（2026-06-30）したためこのレッスンの適用外。これらは `$DATA_DIR/ref/` 直下に配置し git 管理外とする。

- **入力 UI 要件の有無は「補助情報性」で判定する**: 主たる確認手段が別途存在し、その情報なしでも担当者がオブジェクトを一意に識別できるなら補助情報扱いで UI は不要。（例: delete サミットの日本語名は SOTA コード・英名で代替可能なため空欄許容とし、入力 UI を省いた。2026-06-30）

- **データ駆動の確定値はサンプル代表性を先に確認する**: 「全件処理した」という表面的事実だけで確定に踏み切ると地域偏りを見落とす。NODATA / 欠損率が高い場合は実質サンプルの地域・属性分布を確認して代表性を判断し、不十分なら欠損を埋めてから確定する。（2026-05-21）

- **廃止データを母集団に含めない**: 公開リスト（SOTA summitslist.csv 等）に廃止済みエントリが残っていても、`ValidTo` 等のライフサイクル属性を先に確認し、現役のみに絞ってから分析する。（2026-05-21）
