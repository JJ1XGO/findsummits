# Lessons Learned

> 解決済み事象の詳細・パフォーマンス実測値は `mgmt/archive/lessons_archive.md` を参照。
> 未解決バグ・課題は `mgmt/tracker/` で管理（二重管理しない）。

## 設計選好（ユーザー確認済み）

- **運用ミス起因の異常はフェイルファースト**: prefetch 漏れ等、解析対象メッシュにタイルが1枚もない場合はスキップ続行ではなく処理を中止し、原因調査と再実行をユーザーに促す。（2026-06-12: ISSUE-089 FR-004 異常系の書き換えで確認）

## アルゴリズム・実装

- **analysis_count 期待値の仕様（2026-05-02確認）**: 3×3 メッシュ解析の `analysis_count` 期待値は、ピークが何メッシュのコンビネーション画像に含まれるかで決まる。コーナーメッシュ = 4、エッジメッシュ = 6、中央メッシュ = 9。2/3 はフリンジ由来の異常値（BUG-014 修正で解消）。

- **致命的バグ(13b1f72)**: `load_mesh_tile()` でタイル書き込み後に前行を 0 リセットしていた。`calloc` で初期化済みのためリセット不要。タイルを上書きするコードは書く前に「本当に必要か」を確認する。
- **コル検出(c317186)**: Union-Find の `union` 時に `peak_id < 0`（海面コンポーネント）のチェックが抜けていた。海面境界との接触を「コル」として誤検出していた。

## パフォーマンス

- 9メッシュ解析（5339・中心付近）の Union-Find 解析時メモリは max 90.8%（≒57GB）に達した（62.72GB マシンでスワップ使用しつつ完走）。メッシュが中心に近いほど解析範囲が広がりメモリが急増するため、全国解析では同様の状況が発生しうる。詳細実測値は `mgmt/archive/lessons_archive.md` 参照。

## 設計判断

- **フリンジピーク除外アプローチ（2026-05-02確認・BUG-014）**: combined 画像の端タイルはタイル座標の `floor()` 丸め誤差で地理境界より ~17px（~80m）外側にはみ出す。フリンジデータはコル検出に必要なため削除不可。ピーク出力段階（CSV 出力ループ）で地理範囲外を `continue` でスキップするのが正しいアプローチ。Python（merge.py）側でフィルタすると analysis_count / expected_count ロジックへの影響が生じるため C 側で完結させる。

- **DEM1a は不採用**: プロミネンス 150m 判定には DEM5（5m解像度）で十分。DEM1a はデータ量が 25 倍になるが精度向上はほぼない。
- **レベル15→14ダウンサンプリングはmax pooling採用**: プロミネンス計算目的では山頂を保持するmax poolingが適切。キーコルは実際より高く評価されプロミネンスが過小になるが、申請に対して保守的な方向なので許容範囲。NODATAは最大値計算から除外すること。
  - **用途**: 大山・東北の独立峰など、解析範囲内でKeyコルが見つからないピークに対して広域再解析する手段として。
  - **実装方針**: タイルファイルを作るのではなく、レベル15タイルを読み込んで結合する際にmax poolingでレベル14化する。同じメモリで4倍の面積をカバーできる。
  - **実装時の注意点**（漏れチェック）:
    1. **座標変換**: `mesh.c` のタイル座標↔地理座標変換はレベル15前提。レベル14化するとピクセルサイズが2倍になるため変換ロジックの修正が必要。
    2. **col_margin_px**: 現在はレベル15ピクセル単位。レベル14化後は1px=レベル15の2px相当になるため、CSV出力・判定ロジックへの影響を確認すること。
    3. **1pxボーダー**: メッシュ外周の海面ボーダーがレベル14化後は地理的に2倍の幅になる。意図通りか確認すること。
    4. **257×257オーバーラップ**: タイル境界の1pxオーバーラップをmax pooling時にどう扱うか設計が必要。

- **dem10b が存在しないタイルがある（GSI側未整備）**: prefetch しても一部タイルが取得できないのは GSI 側が HTTP 404 を返すため（取得漏れではない）。欠損は南部メッシュ（35.7°N以南）に集中。Cコードは NODATA(-9999) 扱いで解析続行するため動作上の問題なし。terrain PNG での矩形ブロック状の異常はこれが原因。

## プロセス

- **欠陥管理フローの順序**: `bug close` の前に必ず `bug update --status 対応中` が必要。欠陥管理フロー: 発見 → 登録 → 承認 → `対応中` に更新 → 実装 → `make` → `対応完了`（bug close） → ユーザー verify → `解決済`（bug verify）の順を必ず守る。

- **plan.mdを常に最新に保つ**: プロジェクトは plan.md を基準に進める。実装変更・設計変更があった場合は todo.md だけでなく plan.md も必ず更新する。plan.mdが古くなると「設計と実装の乖離」が生じ、次セッション以降の判断が狂う。

## 設計・仕様

- **出力列に複数の概念を混在させない**: merge.py の旧 status 列は「突合結果」（matched/new/deleted）と「解析品質」（confirmed/unstable）が混在していた。申請書作成時に判別できなくなるため、概念ごとに列を分ける（match_status / stability）。

- **設定値は初回から設定ファイルに入れる**: tolerance_px のように「結果を見て調整したい」パラメータは、最初から設定ファイル（fetch_config.ini）に入れておく。コマンドライン引数のデフォルト値を直接書くと、後から「設定ファイルで管理して」と言われる。

- **パスはプロジェクトディレクトリからの相対で**: DATA_DIR（環境依存）配下にソースコード付属のデータ（ref/summitslist.csv）を置く設定は誤り。`Path(__file__).parent.parent` でプロジェクトルートを参照する。

## Patterns to Avoid
*避けるべきパターンを記述すること。ファイルの中身を勝手に消さない。

- **【重大】合意済み仕様の無断変更禁止**: ユーザーと合意した仕様（例: 3×3フルメッシュ解析）を、技術的困難を理由に勝手に変更してはならない。変更が必要な場合は必ずユーザーに状況を説明し、両者の合意を得てから変更する。黙って仕様を変えることは重大な技術者倫理違反である。
- **【重大】許可されたパス以外への書き込み禁止**: dangerouslyDisableSandbox: true が要求される様なコマンドを実行してはならない。書き込もうとしたパスが許可されていない場合は、ユーザーに理由を説明した上で書き込み可能にして貰う事。プロジェクトで許可された範囲以外のコマンドを実行する事は重大な技術者倫理違反である。
- **【重大】指示されたスコープを超えて先に進まない**: 「〜まで」「〜だけ」と範囲が明示された指示は、その境界で必ず止まる。次のステップが明らかであっても、ユーザーの明示的な指示なしに先へ進んではならない。ユーザーが途中で止める理由（タイミングを自分で決めたい・他に確認したいことがある等）は常に存在しうる。「どうせ次もやるから一緒に」という先読みは禁止。（2026-04-24: 「止める所まで」という指示を無視して再実行まで進めてしまった）
- **【重大】テスト・実行前には必ず一旦止まる**: このプロジェクトは扱うデータ量が多く、テスト1回の待ち時間が長い。複数の修正をまとめてからテストしたいので、テスト・解析実行の前には必ずユーザーに確認を取る。「次は明らかにテストだ」と思っても自分で開始してはならない。疑問形のメッセージ（「〜してない？」等）は確認であり実装・実行の指示ではない。答えるだけで止まり、実装・実行が必要なら「やりますか？」と聞く。（2026-04-26）
- **【重大】引き継ぎ資料を表面だけ読んで作業に入らない**: handover や mgmt/plan.md・ADR の「アルゴリズム案」「次にやること」を完全に吸収しないまま設計判断・実装を開始してはならない。前セッションが Plan Phase 1 で中断していたとしても、議論メモには重要な合意内容が残っている。「アルゴリズムは確定済みと判断 → 別の論点（フェーズ配置）だけ詰めれば良い」という早合点が致命的。引き継ぎ資料を読むときは、見出しの言葉（例: 「per-mesh エンジン流用」「段階完了後にピーク統合を再実行」）の**構造的含意**（= ループ構造・既存 FR の再利用）まで読み取ること。表面的な記述だけで判断すると、ユーザーが本来描いていた構造（縮小版パイプラインのループ）を見落とす。（2026-05-18: FR-014 を「フェーズ3 末尾の単発処理 + merged 差分上書き」と書き換え commit し、ユーザーから「私のイメージとは全く異なります」と指摘されてやり直し）
- **フラグ命名は単独の読みやすさと並列フラグ群の真偽値方向の両方を考慮する**: 命名遍歴 `is_tile_top` → `key_col_unresolved` → `key_col_resolved`。`is_tile_top` は「タイル（256×256px）の最頂点」と誤読されやすかったため `key_col_unresolved` に改名し、並列フラグ `area_truncated` と「true=異常」で意味方向を揃えた。しかしユーザーから「肯定形のほうが直感的」との指摘を受け、最終的に `key_col_resolved` + `area_complete`（共に true=正常）に統一。教訓: 真偽値方向の選択は否定形よりも肯定形を優先し、並列フラグ群全体で揃える。単独の名前の良し悪しだけで決めると並列性が崩れる。（2026-05-19）

- **【重大】ユーザーの配置に関する発言は実装方式の含意を含む**: 「フェーズ2 に位置付けたかった」「per-mesh で扱いたい」のような発言は、SRS 上の配置選好だけでなく、**既存エンジンの流用・拡張で実現したい**という実装方式の含意を含むことが多い。配置と実装方式は分離した上で、両方の意図を確認すること。配置だけ受け取って実装方式（差分上書き等の新規ロジック）を勝手に設計してはならない。（2026-05-18: 「フェーズ2 に位置付けたかった」を配置の選好と誤読し、FR-014 を独立した処理として書いてしまった）

- **既存提案の部分修正発言は『追加』か『置換』かを明示確認する**: Claude が提案した複数キーのソート順序に対し、ユーザーが「キー X を最優先、X が同値なら → 北 → 西」と返答した場合、それは (a) 既存の 1 次キーを X に置き換える のか (b) 既存の 1 次キーは維持して X を追加する のかが曖昧。明示されていない部分の扱いを勝手に決めると手戻りになる。複数キーソートのような構造的提案に対する部分修正発言を受けたときは、**残りのキーをどう扱うかを明示確認する**こと。（2026-05-20: ISSUE-019 採番順序で「標高降順 → peak_lat 降順 → peak_lon 昇順」に対しユーザーが「プロミネンスの大きい順、プロミネンスが同じだったら → 北 → 西」と返答。Claude は「標高をプロミネンスに置換」と解釈したがユーザー実意図は「標高は維持しプロミネンスを 2 次キーに追加」だった。SRS / plan / トラッカーを書き直す手戻り発生）

- **【重大】データ駆動の確定値はサンプル代表性を必ず先に確認する**: 「全件処理した」という表面的事実だけで確定に踏み切ると致命的な偏りを見落とす。実行時に NODATA / 欠損率が高い場合は、実質サンプルの地域・属性分布を必ず可視化して代表性を判断する。代表性が不十分なら欠損を埋めてから確定する。（2026-05-21: ISSUE-020 Phase B で delete_zone_max_drop を JA サミット 4,600 件で実測したが NODATA が 3,767 件（82%）あり、実質サンプル 833 件は関東甲信越偏重。最大 abs_diff 17.95m を根拠に 200m で確定した直後、ユーザー指摘で偏りに気付き全国タイル取得→全件再実測で最大 52.26m → 250m に訂正。ADR-SRS-011 と SRS を 2 度書き換える手戻り発生）

- **廃止データを母集団に含めない**: 公開リスト（SOTA summitslist.csv 等）に廃止済みエントリが残っていても、将来仕様の根拠データに含めると外れ値で結論が歪む。`ValidTo` 等のライフサイクル属性を必ず先に確認し、現役のみに絞る。（2026-05-21: ISSUE-020 Phase B 全国実測で JA/HS-243（ValidTo=2020-08-31 廃止サミット）が最大 abs_diff 100.16m となり、これを含めると delete_zone_max_drop が 300m に膨らんだ。廃止 86 件を除外したら 52.26m → 250m に収まった）

- **issue 判定は「出自」ではなく「残作業」で行う**: レビュー派生タスクは「仕様レビュー由来 ＝ 仕様議論を伴う」と誤判定しやすい。しかしレビューで仕様が確定済みで、残作業がコメント修正・命名追従・機械的変換だけなら `todo.md` が正しい。複数件をまとめて登録するときも 1 件ずつ判定すること。（2026-06-08: ISSUE-082〜086 の一括登録で ISSUE-082・086 が違反。06-12 に todo.md へ移行）
