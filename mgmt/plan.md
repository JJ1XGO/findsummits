# FR-014 をフェーズ3 後配置へ移行（ISSUE-033 / ISSUE-021 同時解消）

## Context

ISSUE-033（SRS FR-018 における FR-014 参照記述の整合性修正）の本質的な原因は、
**FR-014 のフェーズ配置自体が論理的に正しくない**ことにある。

- 2026-05-16 に FR-014 を「フェーズ2: per-mesh」へ移したが、SRS FR-018 に旧設計（フェーズ3 後配置）の記述が残っており、循環参照（フェーズ3 出力 → フェーズ2 入力）が発生している
- 朝の議論で「per-mesh 段階では `is_tile_top` を確定できない（隣接メッシュ解析でコルが見つかる可能性がある）」点が論点に上がった
- 実際、SRS FR-008 のフェーズ3 統合は「`(未確定フラグ=0, コル標高が最も高い)` レコードを代表に採用」となっており、**フェーズ3 で `is_tile_top` は解消され得る**構造
- フェーズ2 で先に FR-014 を回すと、本来フェーズ3 統合で `is_tile_top=0` になるピークまで広域再解析してしまう（無駄な処理）

→ **FR-014 はフェーズ3（全国統合）の後に配置するのが論理的に正しい**。
入力は merged.csv + merged_activation.geojson、出力は同ファイルの上書き。
これにより ISSUE-033（FR-018 循環参照）と ISSUE-021（上書きスコープ未明示）が同時解消される。

ADR-004 のアルゴリズム（4×4→5×5 段階拡大、N² スライディングウィンドウ、早期終了、L14 max pooling、
C エンジン拡張による実装）は維持。**変更するのはフェーズ配置と入出力先のみ**。

---

## 変更方針

### フェーズ配置

選択肢を検討した結果、**「フェーズ3 内・FR-018 の後」**配置を採用する。

| 配置 | 採否 | 理由 |
|---|---|---|
| フェーズ3 内・FR-018 の後（採用） | ✅ | フェーズ数を増やさず最小修正。フェーズ3 を「全国統合 + 広域再解析・フラグ解消」と再定義 |
| 新フェーズ3.5 を追加 | ❌ | フェーズ数が増える。責務分離のメリットは小さい |
| 新フェーズ4 として独立 | ❌ | 既存フェーズ4 が繰り下がり波及が大きい |

### 入出力

- **入力**: `$DATA_DIR/results/merged.csv` および `$DATA_DIR/results/merged_activation.geojson`（FR-008 / FR-018 の出力）
- **出力**: 上記2ファイルの該当レコード/ポリゴンを上書き
- **per-mesh ファイル（`<meshcode>.csv` / `<meshcode>_activation.geojson`）は更新しない**（ISSUE-021 案A）

### トリガ条件

ADR-004 のまま:
- `is_tile_top=1`（プロミネンス未確定）
- `area_truncated=true`（アクティベーションゾーン不完全）

ただし「フェーズ3 統合後」に判定するため、対象ピーク数は per-mesh 段階より大きく減る。

### アルゴリズム

ADR-004 のまま:
- 4×4 メッシュ + L14（一次解析）→ 5×5 + L14（自動エスカレーション）
- N² スライディングウィンドウ全パターン探索 + 早期終了
- `area_truncated=true` のみは 4×4 固定
- 5×5 後も残存する場合はログ警告 + フラグ維持で処理継続（手動調査待ち = ISSUE-020 と連携）
