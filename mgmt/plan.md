## Context

`spec-panel` で SRS の **FR-019（HTML ビューア機能仕様）**（`docs/20_SRS.md:1093-1167`）を
4視点レビューした結果、9件の指摘を検出した。最大の論点はデータモデル⇄UI の対応が
宙に浮いている2点（カテゴリ定義の曖昧さ・FR-012 出力経路の欠落）で、放置すると
HLD/実装で解釈ぶれを生む。残りはトレーサビリティの抜けと明文化で解消できる抜け。

下流（HLD/LLD/UT）は未作成ステージのため対象外。仕様優先原則に基づき SRS を正として修正する。

ユーザー指示: **全9件**を対象、**issue/todo に振り分けて tracker 登録**してから着手。

## 実行手順

### Phase 0: tracker 登録（1論点1課題・actor はモデル名）

- issue: `venv/bin/python3 mgmt/tracker/track.py issue add`（type=設計 or 改善）で #2,#3,#4,#5 を登録
- todo: `mgmt/todo.md` に #1,#6,#7,#8,#9 を追記
- 各 issue は作業開始時 `issue update --status 対応中`、決着後 `issue close`

### Phase 1: todo（明文化・追従）を SRS 直接修正

`docs/20_SRS.md` を編集。ドラフト:

- **#1** 1095 行: 対応 UR 欄に UR-011（10_URD.md#ur-011）を併記
- **#6** 入力テーブル(1100) or 各レイヤー記述(1140-1143)の備考に「実行時にブラウザから外部タイル（地理院標高タイル・基準点タイル）を取得する依存」を明示。SRS の外部I/F分類ルール（`docs/CLAUDE.md`）に従い、どこに書くか確認のうえ追記
- **#7** 1138 行「別 ISSUE 管理」→ `track.py issue list` 等で該当 ISSUE 番号を特定して明記
- **#8** 1164 行に「名称変更・座標変更（UR-004『その他』）は自動識別対象外（UR-003）のため本エクスポートの出力対象外」の一文補足
- **#9** 1131/1158 に境界条件を1行補足（座標フォーマット検証・範囲外座標の扱い・localStorage 容量上限は HLD 委譲の旨）

### Phase 2: issue（仕様議論）を1論点ずつ相談→確定→SRS 反映

1論点ずつ合意してから書く（まとめて実装しない）。各論点で FR-009 のデータモデルを確認:

- **#2 カテゴリ定義**: `feature_type`(summit/peak/key_col) × `match_status` × `is_band_change_candidate` と new/dominant/changed/unchanged の対応表を定義。設計判断を含むため **ADR-SRS 候補**
- **#3 FR-012 経路**: FR-012（サミット一覧 申請内容反映版）の生成トリガを確定（推定: FR-021 エビデンス ZIP 同梱）。出力欄(1109)・エクスポート記述(1162)・FR-021/FR-012 本文の整合を取る
- **#4 フィルタ帰属**: delete サミット・key_col を4カテゴリにどう割り当てるか（#2 と連動）を定義
- **#5 山岳名必須性**: new ピーク山岳名の必須/任意、未入力時の申請書(FR-011)挙動（空欄申請 or 警告）を確定。申請成否に影響するため **ADR-SRS 候補**

### Phase 3: 検証・コミット

- `make lint` 警告ゼロ確認（lint-md 等）
- SRS 内・URD への Markdown リンク切れがないか確認（`grep` でアンカー存在確認）
- ドキュメント更新ルール: 更新したターン内に commit（push は別途指示まで不要）。Conventional Commits・本文日本語
- 課題決着分は `issue close`（ユーザーが後で `issue verify`）

## モデル方針

本作業は SRS 文書編集＋ADR 起票＋仕様解釈の判断（特に Phase 2 #2-5）が中心で、
実装ファイル（.c/.h/.py）の単純編集ではない。仕様解釈の判断が頻繁に発生するため
**Opus 継続が望ましい**（原則5 の例外条件に該当）。Sonnet 切替は不要。
