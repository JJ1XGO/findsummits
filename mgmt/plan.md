# SRS パラメータ・引数の記述統一

## Context

`docs/02_SRS.md` の機能要件（FR-XXX）で、入力・引数・パラメータの記述スタイルが機能ごとにバラついている。Explore agent の調査で 5 つのパターンに分類された：

1. **モード分岐式の記述**（FR-004 行271-273）: 「通常モード（N=3）/ 広域モード（N=4/5/6）」— ユーザーが特に懸念した「引数なしなら3×3、ありならN×N」式の How 寄り記述
2. **「（オプション）」の曖昧記述**（FR-008 行369・FR-018 行386）: メッシュコードリストが任意指定だが、未指定時のデフォルト動作が不明確
3. **ファイル名内変数**（FR-017 行172 `{n03_year}`、FR-001 行188 `{dem}`）: 渡し方が機能ごとに違う
4. **定数の置き場混在**: プロミネンス130m（FR-007 本文）vs delete_zone_max_drop=250m（FR-016 `params/config.ini` 明記）
5. **制御フロー混入**（FR-001 行203-206 HTTP 429/503 リトライ条件、FR-009 行524「非ゼロ exit」）: 実装方式の言及

HLD に入る前に SRS で記述規約を統一しないと、HLD で実装方式（CLI 引数 / config.ini / 環境変数）を独立に検討できない。CLAUDE.md の「仕様優先原則」「ドキュメント・実装整合性原則」にも沿わない。

**意図する成果**: SRS から「渡し方」「実装方式」の記述を排除し、「データ」だけを書く形に統一する。HLD は SRS のデータ定義を入力として、CLI/設定ファイル/環境変数の使い分けを独立に設計できるようになる。

## 方針（ユーザー承認済み）

- カスタマイズ可能な項目（プロミネンス閾値・リクエスト間隔・delete_zone 閾値等）は **「名前・意味・デフォルト値・許容範囲」のみ** を SRS に記述
- `params/config.ini` での指定方法、CLI 引数での上書き等は **HLD に追い出す**
- 仕様優先原則に沿った記述

## 推奨アプローチ

### A. データ辞書セクションを新設（02_SRS.md）

SRS の前段に「N. データ辞書」セクションを追加し、入出力データと設定可能項目を一元定義する：

```markdown
## N. データ辞書

### N.1 入出力データ
| データ名 | 意味 | 制約・形式 |
|---|---|---|
| 1次メッシュコード | ... | 4桁数字、範囲 3622〜6848 |
| サミット候補リスト | ... | 緯度・経度・標高・キーコル情報を含むレコード集合 |
| ... | | |

### N.2 設定可能項目
| 項目名 | 意味 | デフォルト値 | 許容範囲 |
|---|---|---|---|
| プロミネンス一次フィルタ閾値 | ... | 130m | 0〜1000m |
| プロミネンス最終フィルタ閾値 | ... | 150m | 0〜1000m |
| delete_zone 比高閾値 | ... | 250m | 100〜500m |
| 解析範囲サイズ N | ... | 3 | {3,4,5,6} |
| ... | | | |
```

機能要件本文ではデータ名で参照し、定義は重複させない。

### B. 機能要件テンプレートの統一

すべての FR を以下の構造に揃える：

```markdown
### FR-XXX 機能名

**概要**: 1〜2文の要約

**入力**:
| 区分 | データ名 | 必須/任意 | デフォルト（任意時） |
|---|---|---|---|
| - | [データ辞書参照名] | 必須 | - |
| - | [データ辞書参照名] | 任意 | [デフォルト動作] |

**出力**:
| データ名 | 形式 |
|---|---|
| [データ辞書参照名] | - |

**処理**: 入力→出力の論理（実装方式に踏み込まない）

**異常系**: 入力不正・データ不在時の振る舞い（exit code 等の実装詳細は HLD へ）
```

### C. 修正の具体例

**FR-004**（モード分岐式 → 任意入力 + デフォルト）:

| 現状 | 修正後 |
|---|---|
| 「通常モード（N=3, L=15）」「広域モード（N=4/5/6, L=14）」を分岐記述 | 入力に「解析範囲サイズ N（任意、デフォルト=3、範囲 {3,4,5,6}）」「使用タイルレベル L（N に従属、N=3 のとき 15、N>=4 のとき 14）」と記述 |

**FR-008/FR-018**（「（オプション）」→ 明示的なデフォルト動作）:

| 現状 | 修正後 |
|---|---|
| 「メッシュコードリスト（オプション。指定時はそのメッシュの CSV のみ読み込む）」 | 入力「対象メッシュコードリスト（任意、未指定時=全メッシュ対象）」 |

**FR-001**（HLD 寄り記述の移管）:

| 現状 | 修正後 |
|---|---|
| HTTP 429/503 リトライ条件、User-Agent 形式、リクエスト間隔を本文に記述 | 設定可能項目「リクエスト間隔」「User-Agent 識別子」のみ SRS に。リトライ条件は「過負荷時は再試行する」と抽象化し、ステータスコード・バックオフ戦略は HLD へ |

**FR-009**:
| 現状 | 修正後 |
|---|---|
| 「非ゼロ exit で終了」 | 「異常終了」と抽象化（exit code は HLD で定義） |

### D. ADR-SRS-014 として規約を永続化

`docs/decisions/ADR-SRS-014-srs-parameter-description-convention.md` を新設。

- **状態**: 採用・未実装（規約策定後、SRS 本体改訂に着手する想定）
- **Context**: 上記「Context」を要約
- **Decision**: A〜C の方針を記述規約として採用
- **Alternatives**:
  - 機能要件内に直接型・引数名を書く（→ 仕様優先原則に反する）
  - データ辞書を作らず各機能で重複定義（→ 整合性維持コスト高）
  - SRS に CLI 引数・config.ini を明記（→ HLD の設計余地を奪う）
- **Consequences**: HLD でのインターフェース設計が独立できる／既存 FR の書き換えコストが発生／用語集（00_GLOSSARY.md）に新規データ用語追加が必要
