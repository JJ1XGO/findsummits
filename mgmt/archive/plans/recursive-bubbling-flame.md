# インシデント即時記録の堅牢化

## Context（なぜ行うか）

前回セッション（b9ffa0ba / 2026-06-25）でインシデントが発生した際、記録ルールが守られず、
最終的に記録ファイルが残らなかった。原因は2層に分かれる:

- **環境側（防げない）**: ToolResult 配送が断続的に空になり、Write / ExitPlanMode 等が機能不全。
  ハーネス/配送系の問題で、モデル側では異常そのものを防げない。
- **記録プロセス側（防げる）**: ①即時発火せず「安定後に記録」と先送りを検討 →
  ②ユーザー指摘でやっと着手 → ③Write の成功表示を信じ **実在検証をしなかった** →
  ④`.claude/incidents/` が空のまま（書込みは実際には失敗していた）。

現行の `log-incident` スキルには「最小記録優先」「書込み後の実在検証」「ツール不調時の人間フォールバック」が
無く、まさに前回つまずいた箇所が手順に入っていない。

**方針**: 異常そのものは防げない以上、対策は「異常のさなかでも記録が確実に残る手順」に絞る。
ハーネス側 hook は配送不調下では同じく無力（hook 自体がツール基盤に依存）なため追加しない
（ユーザー選択 = スキル堅牢化のみ）。記憶上の教訓「記録は配送不調なら hook でも無力、人間経路が最強」に沿う。

## 変更内容: `log-incident.md` を「鉄則 + 四段手順」に再構成

### 冒頭に「鉄則」を新設（前回の3つの失敗に直接対応）

1. **完璧主義禁止**: 整形より先に、まず最小1行でも書く。「後で」「安定後」は禁止。
2. **検証必須**: 書いたら必ず実在確認する。Write/Edit の戻り値だけを信じない。
   実在を確認できるまで「記録した」と報告しない・次の作業へ進まない。
3. **ツール不調時は人間経路へ**: ツールが空結果/失敗を繰り返すなら `!` 手動記録に切替える。

### 対応手順を四段構えに（現行の 1〜2 を置換、3〜5 は維持）

- **段階0 — 即・最小記録**: 検知の瞬間に `.claude/incidents/YYYY-MM-DD_HHmm_<slug>.md`
  （日時は `date '+%Y-%m-%d_%H%M'`、ディレクトリ無ければ作成）へ、時刻と症状だけでも1行書く。
- **段階1 — 実在検証（必須）**: 書込み直後に `cat <file>` か `ls -la .claude/incidents/` で
  ファイルの実在と中身を確認する。確認できるまで完了報告も次工程も禁止。
- **段階2 — 配送不調フォールバック**: ツールが空/失敗を繰り返す（前回の ToolResult 空配送）場合、
  モデルのツール経路は信用できない。ユーザーへテキストで「`!` プレフィックスで以下を実行してください」と
  **完成済みコマンド（heredoc で append）** を提示し、ユーザー経路で記録を確定する。
  `!` はモデルのツール配送を経由しないため配送不調下でも機能する。テンプレを掲載:

  ```
  ! mkdir -p .claude/incidents && cat >> ".claude/incidents/$(date '+%Y-%m-%d_%H%M')_<slug>.md" <<'EOF'
  - 発生時刻: ...
  - 症状: ...
  - 観測出力: ...
  - 状態: 未解決
  EOF
  ```

- **段階3 — 事後の整形・補完**: 環境が安定したら正式フォーマット
  （セッションID `$CLAUDE_CODE_SESSION_ID` / 観測出力 / 推測原因 / 対応 / 状態）へ追記整形する。
- 現行手順 3（ユーザー一行報告）・4（handover 転記）・5（memory/lessons 昇華）は維持。

記載項目（セッションID等）と gitignore に関する注記は現行のまま残す。
