# 計画: グローバル CLAUDE.md コア原則5 の書き換え（モデル切り替え確認の改善）

## Context（なぜ直すか）

前セッションで Opus が「Plan 承認のたびに Sonnet 切り替えを確認するのが面倒」という振る舞いを見せた。
原因を切り分けた結果：

- **ユーザーの運用は健全**（plan を作るか判断 → plan 承認 → 実装、の一貫した流れ）。
- **確認の仕組み自体も必要**。Claude は自分でモデルを切り替えられず（`/model` を打てるのはユーザーだけ）、
  かつユーザーは切り替えタイミングが分からない素人。確認をなくすと Opus のまま実装に突入して無駄になる。
- 面倒がっていたのは Claude（モデル）側であり、ルールの欠陥ではなくモデル一過性の態度の可能性が高い
  （[[incident_model_runaway_not_env]] と同じ筋）。

→ **結論: 確認は残す。削らない。** 改善するのは「確認の質」だけ。
毎回「どちらを推奨するか＋理由＋`/model` 手順」をセットで提示し、ユーザーが推奨に従うだけで
済むようにする（タイミングに悩ませない）。

## 対象ファイル

- `/home/node/.claude/CLAUDE.md` の「### 5. モデルを使い分ける」セクションのみ

## 変更内容（ドラフト）

末尾の「`ExitPlanMode` が承認された直後…1 行で伝える」ブロックを、以下に置き換える：

```
`ExitPlanMode` が承認された直後、ファイル編集を始める前に、**どちらのモデルを推奨するか・その理由・切り替え手順**を
セットで 1〜2 行で必ず伝える。Claude 自身はモデルを変更できず `/model` を実行できるのはユーザーだけなので、
ユーザーが切り替えタイミングに迷わないよう、Claude 側が判断と手順まで示す（ユーザーは推奨に従うか否かを選ぶだけ）：

- Sonnet 推奨時:
  「この実装は〈理由：ファイル編集中心の単純作業 等〉のため **Sonnet** を推奨します。
   `/model` で Sonnet に切り替えてから「続けて」とお伝えください。このまま Opus/Fable で進めることもできます。」
- Opus/Fable 継続推奨時:
  「この実装は〈理由：設計判断が頻発／複雑なアルゴリズム／仕様解釈に揺れ 等〉のため **Opus/Fable 継続**を推奨します。
   モデル切り替えは不要です。このまま進めてよろしいですか？」

いずれの場合も、推奨を曖昧にせず Claude 側が必ず一方を明示すること。
```

既存の前段（「Opus/Fable は調査・設計・判断フェーズ用」「ただし…継続が望ましい場合」の箇条書き、
計画ファイルの詳細度確認の一文）はそのまま維持する。

## 検証

- 書き換え後、原則5 を通読し「確認を残しつつ推奨＋理由＋手順を必ず添える」内容になっていること。
- 他セクション（特に「### 1. 計画を優先する」）と矛盾しないこと。
- グローバル CLAUDE.md なので commit は不要（プロジェクト外・ユーザー個人設定）。
