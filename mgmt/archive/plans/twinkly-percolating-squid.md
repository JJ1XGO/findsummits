# FR-005 ピーク候補リストの定義明確化 + 内部トランザクション定義文の精緻化

## Context

FR-006 レビューに入る前に、FR-005 の出力「ピーク候補リスト」の定義が曖昧な点が判明した。

問題は2つあり、ユーザーとの議論で次のように整理された:

1. **形式欄がトートロジー**: SRS 553 行目の出力テーブルは形式欄が「ピーク候補のリスト」と同語反復で、何の情報を持つリストか分からない。「Union-Find のデータ構造そのものを指すのか？」という疑問を生んでいた。
2. **分類の正当性が読み取れない**: 「内部トランザクション」分類の根拠（ADR-SRS-017）の定義文「独立した**中央データ構造として保持されない**」が多義的で、Union-Find という構造体を持つピーク候補リストや、2次元配列の解析範囲標高グリッドが引っかかって見える。

ユーザーの結論:
- 分類は**内部トランザクションのままで正しい**。ピーク候補リストの座標は解析範囲標高グリッド上のピクセル座標であり、その**解析範囲スコープでのみ有効・解析完了で破棄**される性質だから。
- **ピーク候補リストの中身を明示すれば分類の正当性も自明になる**（論点1を解決すれば論点2も解消する）。
- 内部トランザクションの意味合いが定義文で通じないなら、通じるように該当文書を修正する。

裏付け（調査済み）:
- FR-007 の per-mesh CSV カラムは `peak_lat`/`peak_lon`（緯度経度・SRS 618-619）。内部はピクセル座標で保持し、CSV 化時に緯度経度へ変換している。
- `col_margin_px`（SRS 627）も「解析範囲の端からのピクセル距離」というスコープローカル値。
- → ピーク候補リストの座標がピクセル座標であるユーザーの仮説が裏付けられた。

意図する結果: ピーク候補リストの中身が明示され、内部トランザクション分類の判断基準が「中央データ構造か否か」ではなく「解析スコープローカルで破棄されるか」へ精緻化され、読み手が分類の正当性を自明に追えるようになる。

## 方針

### A. FR-005 出力「ピーク候補リスト」の中身を明示（SRS 553 行目）

形式欄のトートロジーを解消し、コル情報（SRS 580）と同じパターン（形式欄＝型、備考欄＝フィールド列挙）に揃える。各ピーク候補レコードが持つフィールド:

| フィールド | 内容 |
|---|---|
| ピーク座標 | 解析範囲標高グリッド上の**ピクセル座標**（FR-007 で緯度経度へ変換） |
| ピーク標高 | m |
| 所属連結成分の識別子 | Union-Find で管理。FR-006 コル検出・FR-016 ポリゴン生成が参照 |

備考に「座標は当該解析範囲グリッドのスコープでのみ有効で、解析完了後に破棄される（内部トランザクションである理由）」を明記。

### B. 内部トランザクション定義文をスコープ基準へ精緻化（5箇所）

「独立した中央データ構造として保持されない」という構造サイズを示唆する多義的文言を、「**特定の解析処理のスコープ内でのみ有効で、処理完了時に破棄される（永続化されず、後続フェーズや他の解析からは参照されない）**」というスコープ基準へ置き換える。例示も、生 RGB・標高値だけでなく解析範囲標高グリッド・ピーク候補リスト・コル情報といった「大きいがスコープローカルな構造」も内部トランザクションに含まれることが分かるよう補強。

対象（同一定義文を共有）:
- `docs/decisions/ADR-SRS-017-internal-transaction-category.md:16`（定義本体）
- `docs/00_GLOSSARY.md:123`（システム境界・データ分類表）
- `docs/20_SRS.md:109`（2.2 データ辞書の注記）
- `docs/20_SRS.md:1500`（7.2 内部データ一覧の注記）
- `docs/CLAUDE.md:72`（分類ルール表）

### C. ADR-SRS-017 に改訂理由を記録

定義文の変更は判断を伴うため、ADR-SRS-017 の Consequences（または改訂注記）に「中央データ構造基準ではスコープローカルな厚い中間構造を誤排除するため、スコープ基準へ精緻化した」旨を追記する。新規 ADR は作らず既存 ADR の改訂として残す。

### スコープ外（今回はやらない）

- FR-006 本体のレビュー（次の作業）。ただし FR-006 出力「コル情報」形式欄のトートロジー（「コル情報のリスト」）は、FR-006 レビュー時に同パターンで対称化する。
- 実装（src/）の変更。本件は仕様の明確化であり、既存実装は既にピクセル座標で保持しているため追従は不要。
