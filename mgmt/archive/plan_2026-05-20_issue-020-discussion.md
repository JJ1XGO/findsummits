# ISSUE-020: FR-013 / FR-014 手動調査待ちピークの GeoJSON フィーチャ扱い

## ステータス

**議論継続中（未確定）**。2026-05-20 セッションで論点整理を行い、ユーザーが九州・四国実データの削除パターンを宿題として持ち帰り。

## Context

URD/SRS レビュー指摘 H-5。FR-014 で広域エスカレーション後も `key_col_resolved=false` が残るピークの扱いが矛盾している:
- FR-013 では new/dominant のフィーチャ構成にコル等高線ポリゴンが必須
- FR-016 では `key_col_resolved=false` ピークはコル等高線非生成
- `area_complete=false`（旧 area_truncated）が広域でも解消しなかったケースの扱いも未規定

## 議論経過（2026-05-20）

### 出発点（既存 3 案）
- **案A**: 手動調査待ちピークは FR-013 出力から除外
- **案B**: コル等高線フォールバック表現（仮 Polygon / 空 Polygon）
- **案C**: 第 4 の match_status `unresolved` を追加

### ISSUE-019 決定の影響
FR-009 採番順序が「標高 → プロミネンス → peak_lat → peak_lon」と確定。手動調査待ちピーク（プロミネンス未確定）を new/dominant に含めると採番順序が破綻する。
→ **案B は事実上不採用**。残るは A・C。

### 検討した新案

| 案 | 内容 | 評価・結論 |
|---|---|---|
| 案D | 広域モードでコル等高線スキップ。コル等高線外サミットはエラー終了 | 4×4 以上のコル等高線必要性をユーザーが疑問視 |
| 案D' | 広域でも area_complete=true まで継続 | 計算コストが割に合わない |
| 案D'' | C++ エンジンにモードパラメータ追加（コル特定 / ポリゴン生成 / 両方） | SRS L97 改訂が大きい |
| 案D''' | Phase A（コル特定エスカレーション）→ Phase B（ポリゴン生成エスカレーション）の 2 段階 | 標高タイル再読込コストはあるがフローが綺麗 |
| 案D'''' | 広域モードはコル特定のみ。コル等高線ポリゴン外サミットは最近接 `area_complete=false` ピークとペアリング + ワーニング | 富士山・北岳クラスは 6×6 でも完成不能と判断 |
| 案D''''' | `key_col_resolved=false` ピークでも観察可能な暫定 col_elev を取得し、暫定コル等高線ポリゴンを生成 → 各 N×N の暫定ポリゴンを union | 現状 Union-Find に拡張必要 |

### ユーザーの根本的疑問
「ピークとコル等高線ポリゴン内に入らないサミットが本当に発生するか」が不明。
- 頻発するなら案D''''' の意義あり
- レアなら案D'''' + 手動対応で十分
- A99 とは本質的に異なる問題（「人間系では調べようがない」とユーザー認識）

### 現状の Union-Find 実装制約（議論中に確認）
- `src/unionfind.c:167`: 初期値 `col_elev = -9999.0f`
- `src/unionfind.c:183-224`: ピーク合流時のみ col_elev 更新
- `src/analyze.c:169`: `is_top = (p->col_elev < -9998.0f)` で判定
- → **`key_col_resolved=false` ピークの「観察可能な最低コル候補」情報は現状記録されていない**
- 案D''''' 実装には Union-Find の拡張が必要

### 議論内で概ね合意した方針
- 広域モードで「コル特定」と「ポリゴン生成」を毎回両方やるのは計算コスト的に非効率
- 6×6 までやってもコル等高線ポリゴンを完成させるのは富士山・北岳クラスでは現実的でない
- 「広域モードはコル特定が主目的」という方向性は概ね合意
