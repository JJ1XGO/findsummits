# フェーズゲートレビューの導入と SRS→HLD ゲートの実施

## Context

- ユーザーから「各ステージをクローズして次のステージに進んで良いかの確認レビュー（昔のSQAが主催した工程完了審査に相当、現代では phase gate review / quality gate）」を文書化したいとの要望。
- 本プロジェクトのステージ定義は `docs/CLAUDE.md` の採番表（URD→SRS→HLD→LLD→COD→UT→IT→ST→OPS）が既に担っており、プロジェクトマネジメント計画書がなくてもゲートレビューは成立する。
- 現状は「成果物品質」だけが `mgmt/srs_review_progress.md` で厳密管理され、「次ステージ準備」「体制」「リスク管理」の観点は暗黙・会話ベースで通過している。これを定型チェックリスト化する。
- SRS は確定済み・HLD は未着手のため、いま SRS→HLD ゲートを実施するのが最適なタイミング。
- ユーザー確認済みの方針: ①本プロジェクトで先行導入（有用なら後日 dotclaude-ops へ汎用化起票）、②初回適用は SRS→HLD ゲート（URD 分の遡及実施はしない）、③定義・記録とも `mgmt/` に置く。

## タスク（実行モデル: すべて Sonnet 想定、上位モデル委譲該当なし）

### 1. `mgmt/phase_gate.md` 新規作成（定義＋台帳＋初回記録ドラフト）

`srs_review_progress.md` と同じ「冒頭に運用ルール、以下に実施記録」の1ファイル構成。

**定義セクション**:

- 目的: ステージ本体成果物の確定後・次ステージ本格着手前に、クローズ可否をチェックリストで判定するマイルストーンレビュー
- ステージ定義の正は `docs/CLAUDE.md` 採番表（本ファイルでは再定義しない）
- 役割分担: 実施者（資料作成・観点チェック）= Claude、判定者 = ユーザー
- 判定区分: Go ／ 条件付きGo（条件を明記し、次ゲートで消化確認）／ No-Go
- チェック観点（6項目）:
  1. **成果物品質**: レビュー収束・確定（進捗表全Tier完了、ステータス「確定」、lint警告ゼロ）
  2. **未解決課題の処置**: 当該ステージ帰属の open 課題・既知乖離の棚卸しと処置（持ち越し理由明記）
  3. **次ステージ準備**: 進捗管理表・入力成果物・関連 issue 紐づけの整備
  4. **体制**: 要員・経験値のリスク評価と軽減策
  5. **リスク管理**: 台帳・コンティンジェンシーの整備状況（見送りの場合はその判断を理由付きで記録）
  6. **総合判定**: 上記を踏まえユーザーが Go/条件付きGo/No-Go を判定
- ゲート台帳: URD→SRS（導入前のため実施せず、と明記）、SRS→HLD（今回）、以降のゲートは行のみ用意

**SRS→HLD ゲート記録ドラフト**（実施日 2026-07-12）:

- 観点1: `20_SRS.md` 確定（Tier1〜4収束、`mgmt/srs_review_progress.md` 参照）。FR-015 異常系の確定後差分修正は Tier4 再周回不要と判断済み（前セッション決定）
- 観点2: NFR-003 タイブレーク不一致（仕様が正・実装側修正待ち、`mgmt/hld_progress.md` で追跡）、open バグ #16〜#20（実装フェーズ帰属につき本ゲートのブロッカーでない）、ADR-SRS-010 Phase 3〜4（COD 帰属）等の処置一覧
- 観点3: `mgmt/hld_progress.md` 作成済み（FR22＋NFR10＋章4 = 36行）、HLD 関連 issue（#10〜#13, #15）紐づけ済み、テスト文書体系（`02_test_policy.md`・`70_ST.md`）整備済み
- 観点4: 体制 = ユーザー＋Claude。HLD 執筆の経験値少 → リスク評価 M または H（**ユーザーに確定してもらう**）。軽減策: spec-panel 収束ループ継続、設計判断の上位モデル諮問、進捗管理表による分割統治
- 観点5: 専用リスク台帳・コンティンジェンシープランは見送り（プロジェクト規模に対しオーバースペック、2026-07-12 ユーザー判断）。代替機構: GitHub Issues の priority ラベル・ADR の Consequences・hld_progress 備考欄
- 観点6: 判定欄は空欄で作成し、タスク3でユーザー判定を反映

### 2. `/workspace/CLAUDE.md` に運用ルールを追記

「開発ドキュメント管理」節の近くに数行: ステージ本体成果物の確定時（次ステージ本格着手前）に `mgmt/phase_gate.md` のゲートレビューを実施する旨と参照。文書に書くだけだと生成タイミング依存で静かに失効するため、常時注入される CLAUDE.md に判定ステップとして埋める（グローバル best_practices #5）。

- 追記後、hook から claude-md-panel の実行指示があれば従う（前セッション実績のある運用）

### 3. ユーザー判定の取得と記録反映

AskUserQuestion で ①体制リスク評価（M か H か）②総合判定（Go/条件付きGo/No-Go、条件付きの場合の条件）を確認し、`mgmt/phase_gate.md` の記録へ反映する。

### 4. lint・コミット

- 新規ファイルは `git add` してから `make lint`（lint-md は git 管理下のみ対象）で警告ゼロ確認
- Conventional Commits でコミット（例: `docs: フェーズゲートレビューを導入しSRS→HLDゲートを実施`）。push は指示があるまでしない

## 対象外（明示）

- URD→SRS ゲートの遡及実施（台帳に「導入前」と記録するのみ）
- dotclaude-ops への汎用化起票（本プロジェクトでの運用実績を見てから別途判断）
- `docs/00_GLOSSARY.md` への用語追加（ゲートレビューは mgmt/ 内プロセスであり docs/ の製品仕様用語でない）
- リスク台帳・コンティンジェンシープラン自体の作成（見送り判断を記録することが今回のスコープ）

## spec-panel セルフレビューについて

本計画は `docs/` 配下のファイルを作成・更新しない（`mgmt/` とルート `CLAUDE.md` のみ）ため、計画の自動レビュー（/spec-panel）の対象外。

## 検証方法

1. `mgmt/phase_gate.md` が定義＋台帳＋SRS→HLD 記録（ユーザー判定反映済み）を含むことを Read で確認
2. `git add` 後 `make lint` 警告ゼロ
3. `git diff --staged` で意図した変更のみであることを確認してからコミット、`git log -1` で実物照合
