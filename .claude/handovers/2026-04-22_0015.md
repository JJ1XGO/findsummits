## 決定事項

### 解析方式
- **3×3メッシュ方式を正式採用**（合意違反だった BORDER_TILES=8 を廃止）
- **最小矩形最適化**: 隣接メッシュが存在する方向だけ拡張（離島・海岸は 3×3 未満で済む）
- **中心メッシュフィルタ廃止**: 周囲メッシュのピークも出力して後段でマージ

### マージ・突合
- **重複判定**: ズーム15ピクセル座標のチェビシェフ距離。解析結果間の tolerance は 0。**既存 SOTA 突合は別パラメータ**（最初は 0 から始めて結果見て調整）
- **確定判定**: 各メッシュの期待解析回数（隣接存在数から算出）と一致し、全件 `is_tile_top=0` なら確定
- **プロミネンス不安定対応 (D-2)**: analyze.c 側は閾値 130m で出力（余裕持たせる）、merge.py 側で 150m 最終判定
- **コル標高採用規則**: 重複時は `col_elev` 最小を採用
- **境界近接コル**: `BOUNDARY_MARGIN = 256px`（1タイル ≈ 1.2km）、CSV に `col_margin_px` を数値で残しマージで定量比較

### 座標決定論化
- `src/analyze.c` の `cmp_elev_desc` に 2 次キー追加 → **x 優先 → y**（北西側優先、ユーザー指定は x 優先）
- ローカル座標でも順序は一貫するのでグローバル変換不要

### メモリ戦略
- `UnionFind.rank` → int8（-8GB）、`peak_id` → ハッシュマップ化（-10.7GB）
- 3×3 解析のメモリは約 45GB → 約 26GB に削減。並列2が現実的
- 標高は float32 のまま維持（ユーザー希望、精度を下げない）

## 捨てた選択肢と理由

- **18km バッファ（1/4メッシュ）単独**: 150件（3.3%）の取りこぼしが発生するため不採用
- **オフセットグリッド方式単独**: 独立峰・大山・鳥海山・八経ヶ岳等を救えず、運用が複雑。3×3 の素直な解法に回帰
- **RDB 台帳**: CSV マージで足りるなら過剰。Union-Find 状態の持ち越しは更に過剰
- **Union-Find 状態の隣接解析間での引き継ぎ**: シリアライズ・マージの実装コストに対し得られる精度メリットが小さい
- **merge.py での実座標（lat/lon）比較**: tolerance=0 が浮動小数点完全一致になり事実上ゼロ件マッチ。ピクセル座標（整数）比較を採用済
- **`BORDER_TILES=8` の継続**: ユーザー合意違反かつ Key Col が 62km に達するケースあり（is_tile_top=1 は 0.1% だが根本的には不十分）
- **固定 3×3 メッシュ（隣接不在方向も含める）**: 離島・海岸で無駄が出る。最小矩形で最適化する
- **`.mcp.json` と `.claude/settings.json` のコミット**: 明示依頼なし、かつ空ファイル。放置
