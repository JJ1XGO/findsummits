# Best Practices

> `.claude/lessons.md` の221項目を蒸留した高レベル原則集。グローバル層（`~/.claude/best_practices.md`）と
> 重複する原則はここには置かない。詳細な教訓・事例は `.claude/lessons.md` を参照。

このファイルは、221件の具体的教訓に繰り返し現れる「行動の型」のうち、グローバル層（合意の外に出ない／
完了は実物で締める／異常断定の前に構造を疑う／制約は迂回せず設計に吸収／ルールは機構に埋める）で
まだカバーされていないものを17原則に抽象化したもの。
個々の教訓が「何が起きたか」を語るのに対し、ここでは「どう動けば手戻りが減り、効率よく・正しく進むか」を処方形でまとめる。
新しいタスクに入る前にこの一覧とグローバル層を読めば、過去に手戻り・誤解・暴走を生んだパターンを事前に回避できる。
迷ったときの優先順位は概ね「合意 → 検証 → 明示 → 記録」。先に合意と検証を済ませ、決めたことを明示・記録に落とす流れを守る。

---

## 1. 【実データ先行検証】

**何をするか**: 方針・設計を決める前に、必ず実データ（件数・分布・カバレッジ・サンプル代表性）を観測する。直感や「こうすればカバーできるはず」で進めない。

**なぜ有効か**: 実測してから決めるようにしたら、直感を超える値（例外的に大きい距離・想定外の未整備エリア）に基づいて判断できるようになり、後から方針ごと覆る大きな手戻りが減った。

**よくある失敗パターン**: 推測でカバー範囲や閾値を決め、後で実データが想定を裏切って方針・実装ごとやり直しになる。

## 2. 【結果は実物で照合（具体策）】

**何をするか**: ツールの「成功」戻り値やサブエージェントの報告を単独で信用せず、`git diff` / `git log -1` / `ls -la` 等の実データ確認で反映・数値を照合してから完了とする。連続 Edit は各ターン内で差分確認し、リモートの実状態は `git fetch` 後に `origin/*` 同士で比較する。エラーの原因も状況証拠から推測せず、実際のエラーメッセージ文言で特定する。サブエージェントのトレードオフ判断自体は採用してよいが、その根拠となる事実主張（「ツールが何をカバーしているか」等）は必ず一次情報で裏取りする。身に覚えのない差分は mtime で発生タイミングを確認してから扱いを判断する。lint 通過を規約適合の根拠にする前に、その lint の検知パターンが対象の形式をカバーしているかを確認する（パターン外の違反は素通りする）。git 管理下のみを検査する lint では新規の未追跡ファイルが対象に入らないため、新規ファイルは追跡に載せてから lint で確認する。表記レベルの細かい指摘（記号・全角半角等）は数十行前に読んだ記憶で再現せず、提示する直前に該当箇所を再 Read してから出す。

**なぜ有効か**: 戻り値でなく実物を確認する具体的な手段（`git diff`・`ls -la`・`git fetch` 比較・mtime）を習慣化したら、編集漏れ・サブエージェントの数値誤報告・「push が canceled 表示でも実は成功している」といった罠を完了前に検知できるようになった。lint の検査対象範囲（git 管理下のみ）を意識するようにしたら、未追跡の新規ファイルの違反が素通りする盲点を塞げた。長いレビューで離れた箇所を記憶で再現すると記憶混入が起きた実例から、提示直前の再 Read を習慣化した。

**よくある失敗パターン**: 「成功」表示やサブエージェントの報告、UI 上のステータス表示を鵜呑みにして先へ進み、実際とは異なる前提を積み上げて破綻する。

## 3. 【影響範囲を先に洗う】

**何をするか**: 用語置換・リネーム・見出し変更・属性の一括変更など波及する修正は、着手前に `grep` で全出現箇所を機械的に洗い出し（既知のファイル名でなく属性そのもので列挙する）、据え置く分類まで計画に明記してから一括処理する。一括置換・検知に使う正規表現は、複合 ID や非単語文字の隣接で単語境界（`\b`）が不成立になる境界ケースがあるため、既知の実例で較正してから流す。完了後は旧名称の残存ゼロ件と、説明する文書側（README・関連リポジトリ）の追従まで確認する。

**なぜ有効か**: 先に全件を把握するようにしたら、1箇所の変更が20箇所以上に波及するケースでも取りこぼしなく一括処理でき、壊れたアンカーや矛盾の後追い修正が減った。置換パターンを実例で較正するようにしたら、ワイルドカード表記の末尾 `\b` 不成立のような取りこぼしを流す前に検知できるようになった。

**よくある失敗パターン**: 既知の箇所だけ直し、機械列挙すれば見つかったはずのファイルや参照側文書の残存が後のセッションで発覚する。

## 4. 【計画承認後に実装】

**何をするか**: 小修正以外は計画を立ててユーザー承認を得てから実装に入る。計画は対象ファイル・ドラフト・検証手順まで含め、引き継ぎに足る詳細度にする。

**なぜ有効か**: 計画段階で合意を取るようにしたら、実装ターンはトレードオフ議論なしに機械的に進められ、実装中の判断ブレと手戻りが減った。

**よくある失敗パターン**: 計画なしで実装に飛び込み、途中で設計判断が頻発して何度も方針転換し、コミット粒度も乱れる。

## 5. 【状態はファイルに残す】

**何をするか**: セッションをまたぐ重要情報は会話に頼らず永続媒体へ残す。永続性ランクは「トラッカー > plan.md > handover > 会話メモ」。`/clear` の前には必ず handover を実行する。

**なぜ有効か**: 口頭・会話の情報をファイルへ移すようにしたら、コンテキストが消えても作業が継続でき、「以前提示したはずの情報が見当たらない」という再依頼・再調査が減った。

**よくある失敗パターン**: 重要な約束や仕様を会話だけで済ませ、セッション切替後に揮発して誤解・二度手間が生じる。

## 6. 【責務分離と一元化】

**何をするか**: 1つの入力・列・FRに複数の役割を重ねず、役割ごとに分離する。除外・フィルタ等のロジックは一箇所に一元化し、できるだけ早い段階のコンポーネントで適用する。

**なぜ有効か**: 役割を分けて一元化するようにしたら、後段コンポーネントが単純化され、多重フィルタや列の意味の混在に起因する曖昧さが構造的に消えた。

**よくある失敗パターン**: フィルタと統計基準のような別用途を1入力に詰め込み、後で「どちらの意味か」が揺れて分割の手戻りが発生する。

## 7. 【暗黙を排し明示する】

**何をするか**: 「なし＝〇〇」のような不在による暗黙の判別を避け、最初から明示的な値・フラグを持たせる。フォールバック動作・sentinel 値・集約単位の正当性も仕様に明示する。

**なぜ有効か**: 暗黙の判別を明示値に変えたら、将来の拡張で判別ロジックが破綻するリスクが下がり、読み手が独立処理と誤読する事故が減った。

**よくある失敗パターン**: 暗黙のデフォルトや「備考に押し込んだ出力」が下流の入力テーブルと非対称になり、誤読と実装ズレを招く。

## 8. 【要件と方式を分ける】

**何をするか**: 「何を実現したいか（要件・URD）」と「どう実現するか（方式・SRS/ADR）」を分離する。ユーザー要望は要件として記録し、実現方式は ISSUE 経由で下流に委ねる。ADR/URD の見直し要否も既存実装の移行容易性（機械的翻訳のしやすさ等）を主根拠にせず、将来要件（ロードマップ）まで含めた要件面から評価する。「現状維持」を推奨するときは、将来要件で強制される転換と、強制されない選好を区別して提示する。

**なぜ有効か**: 要件と方式を分けたら、上位層が実装詳細に引きずられず安定し、機能要件が揺れたときに上位要件の欠落を疑うという原因追跡ができるようになった。見直し評価を要件面に揃えたら、コードありき（プロトタイプを正とする）の判断をユーザー指摘の前に自分で排除できるようになった。

**よくある失敗パターン**: 要望を聞いた瞬間に設計へ踏み込み、上位要件が不在のまま実装タイミング等が何度も揺れ続ける。既存コードの翻訳しやすさを根拠に「移行不要」と結論し、将来要件からの再評価をユーザーに指摘される。

## 9. 【自動化は制約整合で判断】

**何をするか**: hook・自動化の追加を検討するときは、実装可否だけでなく、入力ファイルの可読性・状態競合などの構造的制約と、既存原則（変更は合意してから 等）との整合性の両面で評価する。新しい仕組みを足す前に既存の必須ステップで代替できないか検討し、目的を達成し終えた防止ルールは定期的に見直して副作用だけが残っていないか確認する。ハーネス・機構（hook・Plan Mode 等)の要求と既存の運用原則（1ファイル原則等）が衝突したときは、どちらかを黙って破らず、機構要求を先に満たしてから統合する段階的手順で両立させる。

**なぜ有効か**: 実装可否だけで判断しないようにしたら、技術的には作れても構造的制約や既存原則と矛盾する自動化（git 管理外ファイルをクラウド実行環境から読む設計など）を作り込む前に気づけるようになった。機構要求との衝突を段階的手順で吸収するようにしたら、既存の完成済み計画を活かしつつ機構のコミット要求も満たせるようになった。

**よくある失敗パターン**: 「作れるか」だけで自動化を設計し、構造的制約を後から発見して手戻りする、または目的を終えた防止ルールを見直さず副作用だけが残る。

## 10. 【横串で漏れを検出】

**何をするか**: 単一要素を閉じて読むのでなく、台帳・一覧から逆引きする横串比較で漏れを探す。過去に直した欠陥が兄弟要素に再発していないか（修正履歴の横展開）、高レベル要約が詳細規定側の変更に追従できているかも確認する。台帳の兄弟項目は参照リンク形式・記述粒度が揃っているのが通常のため、横並び比較で1項目だけの欠落・陳腐化を機械的に見つける。相互参照（supersede 等）は双方向で張られているかも確認する。「section-group単位でレビュー済み」という記録は粒度を保証しないため、必要なら個別要素まで分解して読み直す。

**なぜ有効か**: 横串で見るようにしたら、個別に読むと自己完結して見える要素の構造的な漏れ、同型欠陥の再発、要約と詳細規定の齟齬を検出できるようになった。

**よくある失敗パターン**: 1件ずつ読んで「問題なし」と判断し、要素間の整合・抜けや、粗い粒度のレビュー済み記録の陰に隠れた欠陥を見落とす。

## 11. 【判定基準を先に固定】

**何をするか**: 繰り返す判断（issue/todo の振り分け、トラッカー登録対象の範囲、タイブレーク、並び順・採番、表記ルール、異常系の要否）は、主観でなく客観的な規則として事前に定義・文書化する。異常系の要否のように一見同種に見える判断も、入力の性質（呼び出し元が存在を保証する内部トランザクションか、環境要因で不在になりうる永続データか）まで分けて基準を立てる。

**なぜ有効か**: 判定基準を先に固定したら、毎回考え直す判断コストと表記揺れが減り、同じ議論の再発を防げるようになった。入力の性質まで分けて基準を立てたら、同じ「決定論的処理」でも異常系の要否が分かれるケースを見落とさなくなった。

**よくある失敗パターン**: 基準を決めずその場判断を重ね、表記が揺れたり同じ分類論争を何度も蒸し返したりする。

## 12. 【外部仕様は公式で確認】

**何をするか**: 外部ライブラリ・API・サービス・ハーネス（hook 等）の挙動やURL・規約は記憶に頼らず、公式ドキュメントや実際の呼び出しで確認してから実装する。通常の取得経路が塞がれている場合（許可外ドメイン・画像でしか提供されない定義等）は、ツールの一時ローカル導入や画像の直接確認など確認できる経路へ切り替える。外部ツールの仕様変更に自プロジェクト側の説明文書が追従しているかも定期的に確認し、確認できないものは「未確認」と明示する。

**なぜ有効か**: 公式・実測で確認するようにしたら、存在しないサービス名や誤った前提に基づく実装が減り、根拠のある状態で提案・実装できるようになった。

**よくある失敗パターン**: 記憶した API 仕様で実装し、実在しないエンドポイントや想定外の挙動で動かず、原因調査に時間を取られる。

## 13. 【環境差を前提に確認】

**何をするか**: 実行環境（ホスト/コンテナ、再起動・リビルド前後）でツール可用性・パス解決・設定反映が異なる前提で、作業開始時にどの環境かを確認する。環境依存の処理にはフェイルソフト分岐を入れ、絶対パスのハードコードを避け、設定変更の動作確認は変更が実際に反映される環境（リビルド・再起動後）で行う。環境異常と断定する前に、外部ツール側の設定漏れ・現行仕様の変更を先に疑って確認する。認証情報が複数系統ある環境では、404/403 を「存在しない・権限不足」と即断せず、どの認証情報で実行したかを先に確認する（自動 export されないトークンは毎コマンド明示指定する）。ホスト側の設定値とコンテナ内の実パスが異なるのは仕様のことがあるため、「設定ミス」と断定する前に外部ツールの README で現行仕様を確認する。設定・hook の調査はプロジェクトローカルとグローバルの両層を確認してから「機能が存在しない」と結論する。他プロジェクト・他者からの指摘を受けたら、相手がどのブランチ・どの環境を見ていたかを先に確認する（devel 限定の変更が main に未反映なのは正常にありうる）。

**なぜ有効か**: 環境差を前提に確認するようにしたら、稼働中の環境での確認だけで「反映済み」と早合点する誤判定や、パス焼き込みによるサイレント無効化を事前に防げるようになった。認証系統を切り分けるようにしたら、プライマリトークンでは見えないリポジトリを「存在しない」と誤断定したり、「セカンダリトークンが機能していない」と誤判定して不要な手動作業を依頼したりする事故を防げるようになった。両層確認を徹底したら、片方だけ見て「機能が存在しない」と誤結論する再発を止められた。

**よくある失敗パターン**: 片方の環境でしか解決しないパス・設定を持ち込み、もう一方でエラーが握りつぶされて気づかないまま無効化される。404/403 やトークン変数が空である観測だけを根拠に「存在しない・未設定」と結論する。

## 14. 【症状でなく原因を直す】

**何をするか**: 警告や見た目の不具合は、除外設定・パラメータの微調整といった対症で消さず、原因となる変数を切り分けて特定してから根本を修正する。対症調整を根本修正の代替にしない。

**なぜ有効か**: 原因を切り分けてから直すようにしたら、効果がすぐ頭打ちになる調整の繰り返しや、症状だけ消えて問題構造が残る修正が減り、一度の修正で再発を止められるようになった。

**よくある失敗パターン**: lint 除外や表示パラメータの調整で症状だけを消し、根本の構造が残ったまま別の形で再発する。

## 15. 【一様処理の前に関係性を確認】

**何をするか**: 表記統一・網羅的列挙・一括置換など複数要素に同じ処理を一様に適用する前に、対象間の関係性（並列か従属か、独立処理か共有ループか等）を本文で確認する。直前セッションの同種修正結果も無条件に正とせず、関係性を再確認してから踏襲する。

**なぜ有効か**: 関係性を確認してから一様処理を適用するようにしたら、「網羅的に列挙する」対応が本文の従属関係（単独ダウンロードしない等）を見落として新たな不正確さを生む事故を防げるようになった。

**よくある失敗パターン**: 「網羅性不足」の指摘を受けて要素を並列に列挙し直した結果、実際には一部要素が他に従属しており、本文の規定と矛盾する記述を作ってしまう。

## 16. 【レビューは反復して収束させる】

**何をするか**: 重要な変更（仕様レビュー・文書最適化等）は一度の適用・一巡で完了とみなさず、変更→再レビュー→新たな指摘の発見→再修正のサイクルを回す。反復の収束条件（再周回トリガー）は、周回ごとに違う指摘が出うる非閉集合カテゴリ（表記統一・追記提案等）を含めず、実質的な矛盾・誤り・欠落など閉じた基準に絞る（文書自体の齟齬も読者の追跡可能性に影響するなら実質欠陥として扱う）。確認用の全件周回は個別要素ごとに読み直すより、複数要素をまとめて再読し相互参照・台帳対応を横断的に機械照合する。差分周回は波及先が修正適用後の状態で既に確認済みなら省略してよい（形式手続きより実質的な確認状況を優先する）。

**なぜ有効か**: 反復サイクルを前提にしたら、一度のレビューでは見えない矛盾（新設ルールと既存記述の重複等）を後続の周回で検出できるようになった。収束トリガーを閉じた基準に絞ったら、件数がプラトー化して判定がくじ引き化する状態（51→9→11件で高止まり）を打破できた。まとめ読みの横断照合に切り替えたら、個別読みより速く漏れも少なくなった。

**よくある失敗パターン**: 一度のレビュー・適用で完了とみなして次へ進む、または表記統一のような終わりのないカテゴリを収束条件に含めたままにして堂々巡りになる。実質確認が済んでいる差分周回を形式のために繰り返し、時間だけ消費する。

## 17. 【対外操作は宛先を直前確認】

**何をするか**: クロスリポジトリの issue 起票・コメント等、対外に残る操作は、実行コマンドの引数レベル（`--repo` 等）で宛先・対象の所属を投稿直前に再確認する。「他プロジェクトから issue が来ている」型の依頼は、連携の向き（相手リポジトリ側の issue か、相手発で自リポジトリに起票された issue か）を先に確定し、まず自リポジトリの open issue 一覧から探す。

**なぜ有効か**: 会話内の文脈（「〇〇の open issue」等）だけを宛先の根拠にせず直前の引数レベル確認を挟むようにしたら、誤リポジトリへの投稿リスクを操作前に検知できるようになった。依頼の向きを先に確定するようにしたら、相手リポジトリを探し回る無駄な調査をせずに自リポジトリの一覧から該当 issue へ到達できるようになった。

**よくある失敗パターン**: 会話の文脈だけで宛先を思い込み、投稿コマンドの `--repo` 指定を確認せず実行する。「issue が来てる」を相手リポジトリ側の issue と解釈し、他リポジトリの探索から始める。
