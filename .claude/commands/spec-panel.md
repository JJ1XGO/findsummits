# 多視点パネルレビュー

指定された仕様文書（URD/SRS/HLD/LLD/ADR の章・FR 番号など）を、以下の4視点で
順にレビューし、指摘を一覧化する。引数で対象を受け取る（例: `/spec-panel FR-013`）。

## 前提ルール（厳守）

- 仕様優先原則: コードを正として参照しない。仕様書の内容を正とする
- 自動 spawn 禁止: 既定は4視点をインラインで順に実施。並列は明示指示時のみ
- 課題登録はしない: 指摘を洗い出して提示するまで。tracker 登録はユーザー承認後

## 4つの視点

1. アーキテクト: モジュール分担・ADR 整合・設計の一貫性・拡張性
2. 仕様レビュアー: URD↔SRS↔HLD↔LLD トレーサビリティ・曖昧さ・抜け漏れ・矛盾。加えて
   **横串の規約適合**: 入出力テーブルが全外部I/F を列挙しているか・他 FR と粒度（記載項目の細かさ）が
   揃っているか・`docs/CLAUDE.md` の分類規約（外部I/F／ユーザー入力／内部データ等）に適合するか・
   **§6 との分類二重定義チェック**: §6 外部I/F一覧と FR 入出力テーブルで同一ファイルの分類（外部I/F vs
   内部データ）が一致しているか（参照形態によって分類が変わりうる点に注意）・
   **手順と終了条件の分断チェック**: 実行フロー（手順1〜N）の記述と終了条件・パラメータ管理が
   分断されていないか（分断は読者の混乱を招く）
3. データ/アルゴリズム: 境界条件・NODATA・サンプル代表性・性能/メモリ
4. 申請者/エンドユーザー: SOTA 申請 O/P 要件・エビデンス妥当性

## 手順

1. 対象文書（引数）を読む。関連する URD/SRS/HLD/LLD/ADR も必要に応じ参照
2. 各視点で指摘を抽出（根拠主義: 推測でなく文書の記述を引用して指摘）
   - **横串比較（必須）**: 単一 FR/章が対象でも、その入出力テーブルを**兄弟 FR の同種テーブル**および
     `docs/CLAUDE.md` の分類規約と相互比較する。失敗モードに注意——単一 FR を閉じて読むと、
     抜けている外部I/F も説明欄・§6 に記載があるため自己完結して見え、見落とす。
     「他 FR は載せているのにこの FR だけ載せていない」項目を能動的に探すこと
   - **§7.2.1 逆引きチェック（必須）**: §7.2.1 内部データ一覧を開き、対象 FR が生成元・参照先として
     漏れなく記載されているかを台帳側から確認する（「FR 内から外を見る」に加えて「台帳から FR を逆引き」
     する。台帳の漏れは実装時に当該 FR が見落とされるリスクになる）
3. 指摘を「視点 / 重要度（高・中・低）/ 内容 / 該当箇所 / 推奨対応」の表に集約
4. 視点横断の総評（最大の論点・トレードオフ）を 3〜5 行で
5. ユーザーに提示し、tracker 登録要否を確認（登録時は 1 論点 1 課題で issue/todo 振り分け）
