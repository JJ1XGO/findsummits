# ADR-SRS-014: SRS 機能要件のパラメータ・引数記述規約

| 状態 | 採用・未実装 |
| 決定日 | 2026-05-31 |

## Context

`docs/02_SRS.md` の機能要件（FR-XXX）で、入力・引数・パラメータの記述スタイルが機能ごとにバラついている。調査で以下の 5 パターンが混在することを確認した：

1. **モード分岐式の記述**（FR-004）: 「通常モード（N=3, L=15）/ 広域モード（N=4/5/6, L=14）」のように、引数の有無・値によって「〇〇モード」と名付けた処理分岐を機能要件内に記述している。これは実装レベルの記述（How）であり、SRS が記述すべき「何を入力するか・未指定時のデフォルトは何か」（What）と混在している。

2. **「（オプション）」の曖昧記述**（FR-008・FR-018）: 「メッシュコードリスト（オプション。指定時はそのメッシュの CSV のみ読み込む）」のように、任意指定であることは示しているが、未指定時のデフォルト動作が曖昧。

3. **ファイル名内変数**（FR-001・FR-017）: `{dem}`・`{n03_year}` のような変数をファイルパス内に埋め込む形式でパラメータを表現しており、入力の渡し方が機能ごとに統一されていない。

4. **定数の置き場混在**: プロミネンス一次フィルタ閾値 130m は FR-007 本文に直書き、delete_zone 比高閾値 250m は FR-016 本文に `params/config.ini` への記述として明記されており、設定可能項目の定義場所が統一されていない。

5. **制御フロー・実装方式の混入**（FR-001・FR-009）: HTTP 429/503 リトライ条件やバックオフ戦略、「非ゼロ exit で終了」のような実装依存の記述が機能要件に含まれている。

この状態で HLD に進むと、CLI 引数・設定ファイル・環境変数の使い分けを SRS に拘束された形でしか設計できなくなり、実装自由度が失われる。また、SRS の「仕様優先原則」（CLAUDE.md）に反して実装詳細が仕様書に先行する構造になる。

## Decision

以下の記述規約を SRS に適用する。

### 規約 1: データ辞書セクションを設け一元定義する

SRS の前段に「データ辞書」セクションを新設し、入出力データと設定可能項目を一元定義する。

**サブセクション構成**:

| サブセクション | 内容 |
|---|---|
| 入出力データ | データ名・意味・制約・形式 |
| 設定可能項目 | 項目名・意味・デフォルト値・許容範囲 |

機能要件の本文ではデータ辞書の名称を参照し、同一データの定義を重複させない。

**設定可能項目の記述対象**: ユーザーまたは運用者が調整可能な閾値・パラメータ（プロミネンス閾値、解析範囲サイズ N、リクエスト間隔、delete_zone 比高閾値等）。これらは「デフォルト値と許容範囲」だけを SRS に記述し、「どのファイル・引数で渡すか」は HLD に委ねる。

### 規約 2: 機能要件は統一テンプレートで記述する

すべての FR を以下の構造で統一する：

```
概要（1〜2文）

入力:
| データ名 | 必須/任意 | デフォルト（任意時） |
|---|---|---|
| [データ辞書参照名] | 必須 | — |
| [データ辞書参照名] | 任意 | [未指定時の動作] |

出力:
| データ名 | 形式 |
|---|---|
| [データ辞書参照名] | — |

処理（入力→出力の論理。実装方式に踏み込まない）

異常系（入力不正・データ不在時の振る舞い。exit code 等の実装詳細は HLD へ）
```

### 規約 3: 「引数有無による挙動変化」は「任意入力 + デフォルト動作」で表現する

「引数なしなら 3×3 処理、引数ありなら N×N 処理」のような実装依存の分岐記述は使わない。代わりに「解析範囲サイズ N（任意、未指定時=3、許容範囲 {3,4,5,6}）」のように、データ名・任意/必須・デフォルト値・制約として記述する。これにより CLI 引数・設定ファイル・環境変数のどれで渡すかは HLD が自由に決定できる。

### 規約 4: 実装方式の記述は HLD へ追い出す

SRS に書かないこと：
- `params/config.ini`・コマンドライン引数・環境変数などの受け渡し形式
- HTTP ステータスコード・リトライ条件・バックオフ戦略の具体値
- exit code の数値
- ファイル名パターン内の変数埋め込み（`{dem}`・`{n03_year}` 等）

これらは「設定可能項目として取得する」「通信エラー時は再試行する」「異常終了する」のように抽象表現に置き換え、詳細は HLD で定義する。

## Alternatives

### 案 A: 機能要件内に引数名・型を直接記述する（不採用）

各 FR に「`--mesh_n` 引数（int、デフォルト 3）」のように書く案。記述が具体的で分かりやすい反面、CLI 設計の決定が SRS 段階に引き込まれ HLD の自由度を損なう。仕様優先原則（CLAUDE.md）に反し、SRS が実装仕様書を兼ねてしまう。

### 案 B: データ辞書を作らず各機能で重複定義する（不採用）

各 FR の入力欄にデータの制約・デフォルト値を直接書く案。初期記述は簡単だが、同一データが複数 FR で参照される場合に整合性維持コストが高くなる。プロミネンス閾値など横断的なパラメータの変更時に全 FR を更新する必要が生じる。

### 案 C: SRS に CLI 引数・config.ini のパスを明記する（不採用）

現状の一部の FR（FR-016・FR-017 等）がこの形式。実運用のイメージが分かりやすいという利点はあるが、実装方式が SRS に固定されてしまう。HLD でインターフェース設計を見直す際に SRS の書き直しが必要になり、「仕様変更」と「実装方式変更」が区別できなくなる。

## Consequences

### メリット

- HLD でのインターフェース設計（CLI/設定ファイル/環境変数の使い分け）を SRS に縛られずに設計できる
- データ辞書一元管理により、パラメータ変更時の更新箇所が明確になる
- FR の記述粒度が統一され、SRS レビューの基準が明確になる

### デメリット・コスト

- 既存 FR の書き換えコストが発生する（FR-001〜FR-018 の全面改訂）
- データ辞書セクションの新設により `docs/02_SRS.md` の構造が大幅に変わる
- `docs/00_GLOSSARY.md` にデータ辞書で導入した新規データ名の概念定義追加が必要

### SRS への変更概要

| 対応内容 | 対象 FR |
|---|---|
| モード分岐 → 任意入力+デフォルト | FR-004 |
| 「（オプション）」→ 明示的デフォルト動作 | FR-008・FR-018 |
| HLD 寄り記述（HTTP リトライ等）の抽象化 | FR-001 |
| 「非ゼロ exit」→「異常終了」への置き換え | FR-009 |
| 設定可能項目のデータ辞書化（本文直書き廃止） | FR-007・FR-016 |
| ファイル名内変数 → データ名での参照に変換 | FR-001・FR-017 |
