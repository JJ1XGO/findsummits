## A. 言語選定: Rust vs C++

### 特徴比較

| 観点 | Rust | C++ |
|---|---|---|
| メモリ安全性 | 所有権・借用システムでコンパイル時保証（GC なし） | 手動/半手動（スマートポインタ併用）。安全性はプログラマ依存 |
| 言語機能 | パターンマッチング・代数的データ型・トレイトが最初から統合 | テンプレートメタプログラミング等、後方互換重視で仕様が肥大化 |
| パッケージ管理 | Cargo（公式・標準） | CMake/Make 等、プロジェクトごとに不統一 |
| エコシステム成熟度 | 発展途上（歴史が浅い） | 歴史が長く実績・ライブラリが豊富 |
| 学習コスト | 高い（borrow checker との格闘） | 低〜中（ただし言語仕様自体は複雑） |

### パフォーマンス

基本的に同等。「Rust の方が速い」と単純には言えない。

- 両言語ともゼロコスト抽象化志向で GC なし。LLVM バックエンドを共有することが多く、最終的な機械語レベルでは近い性能になりやすい
- ベンチマークサイト（Benchmarks Game 等）でもタスク依存で一貫した優劣はない
- Rust が有利になりやすい場面: 所有権システムにより安全かつ高速な並行処理を書きやすい
- C++ が有利になりやすい場面: 枯れたコンパイラ最適化・SIMD 等の極限チューニングが必要な場面
- Rust はデフォルトで配列境界チェック等の実行時チェックが入る箇所があり、わずかなオーバーヘッドが出ることがある（`unsafe` やイテレータ最適化で回避可能）
- 実測差の多くは言語仕様よりアルゴリズム・書き方に起因する

## B. Rust での OpenCV 利用

`opencv` クレート（[twistedfall/opencv-rust](https://github.com/twistedfall/opencv-rust)、crates.io 提供）経由で利用可能。

- 内部的には C++ で書かれた OpenCV 本体を FFI 経由でラップしたバインディング
- core / imgproc / imgcodecs / videoio / objdetect / dnn / features2d 等、主要モジュールの多くに対応
- 導入時の注意点:
  - OpenCV 本体（C++ 版）のシステムへの事前インストールが必要（`libopencv-dev` 等）
  - ビルド時に OpenCV ヘッダを解析してバインディング生成するため clang（bindgen）が必要、初回ビルドが重い
  - インストール済み OpenCV バージョンとクレート対応バージョンの不一致でハマりやすい
- 代替: OpenCV 本体への依存を避けたい場合、Rust ネイティブの `image`（読み書き・基本処理）・`imageproc`（フィルタ・エッジ検出）・`ndarray`（数値配列）クレートも選択肢

## C. gccrs（GCC 上の Rust 実装）の現状（2026-07 時点）

まだ実用段階に達していない。

- borrow checker 未搭載。将来的に Polonius（別プロジェクトの借用チェックアルゴリズム）を統合予定
- 2026 年の目標は「gccrs がカーネルを（不完全にでも）コンパイルできるようになること」（2025-12 時点の報告）
- libcore のビルドは早ければ 2026 年初頭にも可能な見込みだが、完全に正しくコンパイルできるわけではない（2026-03 時点報告）
- マイルストーンは「組み込み向け」「Linux 向け」「汎用コンパイラ」の順に整理されており、組み込み向け（core クレートのみ依存）から実用化を目指す段階
- 2026-09（RustConf・EuroRust）までにカーネルのコンパイルを試みる目標があるが、これは「クラッシュせず取り込める」段階を指し、生成バイナリの正当動作は意味しない
- 代替の `rustc_codegen_gcc`（GCC のコード生成レイヤーに rustc を接続）も存在するが利用者は少なく、標準ライブラリのアーキテクチャ対応問題は未解決
- **結論**: 通常の開発用途では、公式の LLVM ベース `rustc`（Cargo 経由）が現時点で唯一の実用的選択肢。gccrs は本番利用にはまだ早い

## D. 巨大配列のメモリ管理（systemd-oomd）

Union-Find・標高配列等の巨大メモリ確保がホスト全体のフリーズを招くリスクへの緩和策として挙がった話題（言語選定とは独立）。

- Debian testing では `apt install systemd-oomd` で導入可能
- 前提として PSI（Pressure Stall Information）カーネル機能が有効である必要がある（`/proc/pressure/memory` で確認、無効なら GRUB に `psi=1` 追加）
- `/etc/systemd/system.conf.d/` に `DefaultMemoryAccounting=yes` を設定
- 個別プロセスには `systemd-run --scope -p MemoryMax=... -p ManagedOOMMemoryPressure=kill -p ManagedOOMMemoryPressureLimit=80%` で監視ポリシーを付与し、メモリ圧力超過時にそのプロセスだけを kill させ、マシン全体のフリーズを防ぐ
- swap は完全に無効化せず適量残す方が良い（systemd-oomd が反応する猶予時間を確保するため。swap ゼロだと反応前に livelock に陥りやすい）

## E. Union-Find 分割によるスケーラビリティ（3×3 メッシュ制約の再検討材料）

現行の Union-Find は「標高の高い方からグローバルに連結していく」処理のため、単純なタイル独立処理はできない、という制約についての議論。ただし**境界情報だけを橋渡しする階層的 Union-Find**であれば分割可能、という提案。

### 方式1: タイルごとのローカル Union-Find + 境界マージ

- 各タイル（3×3 メッシュ、あるいはさらに細かい単位）内で独立に標高降順ソート + ローカル Union-Find を実行
- タイル境界 1 ピクセル分だけ「境界ラベル・標高・ローカル root ID」を保存（全体のごく一部なので軽量）
- 全タイル処理後、境界グラフのみを使ってグローバル Union-Find を標高順に実行（境界ピクセル数は全体の数% 程度）
- グローバルマージ結果（「タイル A の root X とタイル B の root Y は同一連結成分」）を使い、各タイルのローカルラベルをグローバル ID に変換
- 実装例: **Parallel Priority-Flood**（Barnes, 2016）が DEM の窪地埋め・流向計算でこの発想（タイル分割 + 境界マージ）を採用している

### 方式2: 標高バケツ分割によるストリーム処理

- 標高値を範囲ごとのバケツ（例: 100m 刻み）に分け、各タイルを読みながら該当バケツへ座標を追記（外部バケツソート）
- 標高が高いバケツから低いバケツへ順に処理し、その都度 Union-Find 操作を実行
- Union-Find の parent 配列自体はグローバルに 1 つ必要だが、標高データ本体より遥かに軽量

### データ型によるメモリ削減

Union-Find 本体は整数配列 2 つが本質。標高やその他中間配列（float64 複数枚）に比べ軽量化余地が大きい。

| 配列 | 型 | 1 ピクセルあたり |
|---|---|---|
| parent（親ポインタ） | int32 | 4 バイト |
| rank/size | int16〜int32 | 2〜4 バイト |
| 標高（参照用） | int16（cm 単位） | 2 バイト |

union by rank + path compression（経路圧縮）を併用すれば実行時間・配列サイズとも最小化できる。

### mmap によるディスク退避

グローバル parent 配列が RAM に収まらない場合、この配列だけを mmap でディスクに置く選択肢がある。Union-Find はランダムアクセスが多いが、経路圧縮によりアクセスパターンが局所化していくため、標高データ全体を mmap するより被害が少ない（Rust: `memmap2`、C++: `mmap()`）。

### 既存ツール（車輪の再発明回避の選択肢）

- **RichDEM**（C++/Python）: Parallel Priority-Flood を実装済み。タイル分割・境界マージによる大規模 DEM 処理に対応
- **WhiteboxTools**: 大規模ラスタのメモリ効率的な地形解析ツール群
- **GRASS GIS r.watershed**: リージョン分割処理に対応した流域解析

### この論点がプロジェクトに持つ含意

上記が実現可能であれば、3×3 メッシュ単位（[ADR-SRS-003](../ADR-SRS-003-3x3-mesh-analysis.md)）に限らず、より広域（将来的には日本全土）を一括解析できる可能性がある、という着眼点。現行の広域解析（[ADR-SRS-004](../ADR-SRS-004-level14-max-pooling-isolated-peaks.md) の L14 max pooling 広域再解析）との関係整理も含め、実現可能性・実装コストの検証が必要。
