# ADR-SRS-039: モックアップの位置付けと仕様への反映方針

| 状態 | 採用・実装済み |
| 決定日 | 2026-06-27 |

## Context

HTML ビューアのモックアップ（`docs/mockup/viewer_mockup.html` ＋ `docs/mockup/summits_data.js`）は、
ビューアの UI（レイアウト・操作・配色・マーカー形状等）を実機で確認しながら確定させるために作られた
プロトタイプである。しかし SRS からは [6.6](../20_SRS.md#66-出力-geojson作業用-html-ビューア)・
[6.13](../20_SRS.md#613-出力-公開用-html閲覧専用ブラウザダウンロード) で「画面サンプル」として
リンクされるのみで、**その位置付け（プロトタイプか正式か・更新方針・SRS/HLD/LLD との関係）が
文書化されていなかった**。参照者はモックアップを正式仕様と取り違える余地があり、また
「モックアップの内容をどのドキュメントへどの粒度で反映するのか」の運用も未定義だった。

一方、本プロジェクトには **仕様優先原則**（CLAUDE.md）があり、「コードは暫定的な副産物で、
URD/SRS/HLD/LLD が正」と定めている。モックアップ（HTML/JS）もこの意味では「コード相当」であり、
位置付けを誤ると「モックアップを正とする」運用に流れて仕様優先原則と矛盾しかねない。

現状の事実:

- SRS は既にモックアップの**観測可能な挙動**をほぼ網羅している（[FR-019](../20_SRS.md#fr-019-html-ビューア機能仕様)・§6.6・§6.13）。
- 配色の具体値・マーカーサイズ段階・`maxBounds`・z-index 等の**実装具体値**は、SRS が明示的に
  「HLD に委ねる」としている（[FR-019](../20_SRS.md#fr-019-html-ビューア機能仕様) だけで約9項目）。
- `docs/30_HLD.md`・`docs/40_LLD.md` は未作成。そのため HLD 相当の UI 具体値は、現時点では
  事実上モックアップが保持している。

## Decision

1. **位置付け**: モックアップを「UI を確定させるためのプロトタイプ（紙芝居レベル）」と位置付ける。
   逐次更新し、UI の現行確定状態を表す参照物とする。

2. **正は仕様書**: ただし**正は依然として SRS/HLD/LLD** であり、モックアップは権威ではない。
   モックアップは UI を実機で確認・確定する**手段**であって、確定した内容は仕様書へ反映して
   初めて正式になる。仕様優先原則は維持する。

3. **反映の粒度（どこへ何を書くか）**: モックアップから取り出した内容は、粒度で行き先を分ける。
   - **観測可能な挙動**（何を・どう振る舞うか。表示要素・操作フロー・初期状態・入出力）→ **SRS**
   - **実装具体値・実装方式**（配色値・サイズ段階・レイアウト寸法・`maxBounds` 等パラメータ・
     z-index・描画方式・テンプレート構造）→ **HLD/LLD**

4. **暫定保持と抽出**: HLD/LLD 未作成の現段階では、HLD 相当の UI 具体値はモックアップが暫定保持する。
   HLD/LLD 起票時に、モックアップから該当具体値を抽出して各ドキュメントへ記録する。

5. **同期と除外**: モックアップと仕様の乖離が生じたら、ドキュメント・実装整合性原則に従い同期要否を
   判断する（UI 挙動の変更は SRS、具体値は HLD/LLD にも反映）。なお、モックアップに埋め込まれた
   **サンプルデータ（例示フィーチャ）は仕様ではない**ため、仕様反映の対象外とする。

## Alternatives

**B. いま HLD（`docs/30_HLD.md`）を起こして具体値を抽出する**（不採用）
モックアップは具体値を保持しており HLD 化は可能だが、本プロジェクトはウォーターフォールで SRS 段階に
あり、段階を飛ばさない方針。HLD 起票は次段階で行い、本 ADR はその際の抽出運用を定めるに留める。

**C. モックアップを UI の正（authority）とする**（不採用）
更新の手軽さはあるが、仕様優先原則（コード/モックを正にしない）に正面から反する。乖離時に
「どちらが正か」が崩れ、文書の信頼性を損なう。

**D. 位置付けを書かず現状維持（画面サンプルのリンクのみ）**（不採用）
参照者がプロトタイプか正式かを判断できず、反映運用も定義されないまま。本 ADR の動機そのものを
放置することになる。

## Consequences

- モックアップの位置付けが明確化し、参照者が「プロトタイプ（正は仕様書）」と理解できる。
- モックアップ更新時に「観測挙動→SRS／具体値→HLD/LLD」という反映要否判断の運用が生じる
  （`docs/CLAUDE.md` に明文化）。
- HLD/LLD 起票時の作業に「モックアップからの具体値抽出」が明示的に組み込まれる。
- サンプルデータの正誤はモックアップ品質の問題であり、仕様反映とは切り離して扱える。
- 仕様優先原則と矛盾しない形で、UI を実機検証で固めるワークフローが正当化される。
