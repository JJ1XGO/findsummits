## Context

3×3 メッシュ解析（解析半径 74km）では、大山・鳥海山のように Key コルが非常に遠い独立峰で
`key_col_resolved=false`（Key コル未発見）が残る。さらに、アクティベーションゾーンが解析境界で
途切れる `area_complete=false` も同様に FR-009 の突合精度を損なう。

### データによる裏付け（2026-05-09 確定）

全 JA サミット中、最難度の **Points=10（511 件）** を対象に親ピーク距離（Key Col 距離の
保守的上限）を調査した結果（`research/6x6-mesh-keycol-coverage-study.md`）:

| メッシュサイズ | 解析半径 | カバー率（代理指標ベース） | 推定メモリ |
|---|---|---|---|
| 3×3 | 74 km | 98.2%（9件未カバー） | ~57 GB（実測） |
| 4×4 | 111 km | 99.0%（5件未カバー） | ~25 GB |
| 5×5 | 148 km | 99.2%（4件未カバー） | ~39 GB |
| 6×6 | 185 km | 99.4%（3件未カバー） | ~57 GB |
| 8×8 | 259 km | 100.0% | — |

#### 代理指標の限界と地図目視による補正（2026-05-09 追加確認）

上記の代理指標（最近接の高い SOTA 登録サミットまでの距離）は保守的な上限推定であり、
**Key Col の実際の位置はそれより近い**。特に、親ピークへの方向が E-W 方向の場合、
保守値（緯度方向 74km）が過大になる。

3×3 未カバー9件すべての親ピーク接続線を地理院地図で目視確認した結果
（`research/outliers_3x3_parent_connection.geojson`）:

| 区分 | 該当サミット | 根拠 |
|---|---|---|
| **3×3 内に収まる（7件）** | JA/TT-001 大山、JA/AM-001 岩木山、JA/IT-001 岩手山、JA/TG-001 白根山、JA/NI-007 大日岳、JA/HG-001 氷ノ山、JA/NN-001 奥穂高岳 | 親ピーク方向が E-W、または線が短く 3×3 範囲内に収まることを目視確認 |
| **3×3 外・要対応（確定）** | JA/YM-001 鳥海山（新山） | 親ピーク方向が N-S（保守値と一致）、線が明らかに 3×3 を超える |
| **3×3 外・要検討** | JA/NR-001 八経ヶ岳 | 大山との直線距離は 3×3 内だが、Key Col が琵琶湖周辺を迂回する可能性があり 4×4 でカバー見込み |

**実質的に広域再解析が必要なのは鳥海山（確定）と八経ヶ岳（検討中）の 1〜2 件**であり、
「3×3 で 9 件未カバー」は代理指標の過大推定による見かけ上の数値である。

## Decision

- **パイプライン配置**: フェーズ3.5（FR-008 + FR-018 の全国統合が完了した直後、FR-009 突合より前）。per-mesh フェーズ2 で判定する設計は採らない（同一ピークが複数の per-mesh 解析に出現するため、`key_col_resolved=false` は per-mesh 段階では確定せず、全国統合後でないと真に独立峰となるピークを特定できない）
- **入力**: `$DATA_DIR/results/merged.csv`（FR-008 出力）
- **トリガー条件**: merged.csv 上で `key_col_resolved=false` のピークを対象とする（ADR-SRS-011 によりトリガーを縮小、`area_complete=false` はトリガー対象外）
- **基本方針: 縮小版パイプラインのループ**（ループはコル充足判定 FR-022 が制御、広域モード固有のオーケストレーション責務は FR-014 が担う。FR-004 は 3×3 通常モード専用に純化し、広域モードには関与しない）:
  - **FR-014（広域結合解析オーケストレーション）** が「処理モード（メッシュ数 N + ズームレベル L=14）」「対象ピーク座標リスト」「日本全土1次メッシュコードリスト」を入力に取り、N×N + L14 構成で標高地形図出力（FR-015）と per-mesh パイプライン（FR-005→FR-006→FR-007）を呼び出して**広域 per-mesh CSV を新規生成**する（FR-016 のポリゴン生成は呼び出さない。FR-015 は広域でも呼び出し、解析範囲の目視確認を可能にする）
  - 対象ピークの所属メッシュ単位グルーピング・4 コーナーパターン生成・対象ピーク絞り込み・早期終了といった「広域モード固有のオーケストレーション」は FR-014 内部に内包する
  - per-mesh パイプライン（FR-005/FR-006/FR-007）は FR-004（3×3 通常モード）と FR-014（広域モード）の双方から呼び出される共通サブ処理として位置付ける。タイル結合・標高解析・ピーク/コル検出ロジック自体は N の値・ズームレベルによらず共通（[ADR-SRS-010](ADR-SRS-010-cpp-opencv-migration.md) 移行後の C++ エンジンを共有）
  - 通常 per-mesh ファイル群と広域 per-mesh ファイル群を**まとめて** FR-008 に再投入し、`merged.csv` を再生成する（広域モードは GeoJSON を生成しないため FR-018 は再入しない）
  - FR-008 の重複排除ロジック `(key_col_resolved=true, コル標高最高)` により、広域モードで解消された結果が自動的に代表として採用される（merged への差分上書きはしない）
- **エスカレーション（N = 4 → 5 → 6、FR-022 コル充足判定が管理）**:
  - **一次解析: 4×4 メッシュ + L14**（解析半径 111 km、推定メモリ ~25 GB）
    - 鳥海山（JA/YM-001）: Key Col は 4×4 内に確実に収まる
    - 八経ヶ岳（JA/NR-001）: Key Col が琵琶湖周辺を迂回する可能性があるが 4×4（111 km）でカバー見込み
  - **5×5 + L14**（148 km、~39 GB）— 4×4 後も対象ピークの `key_col_resolved=false` が残る場合に自動実行
  - **6×6 + L14**（185 km、~57 GB）— 5×5 後も残る場合に自動実行（最終段階）
  - **最終残存**: 6×6 後も `key_col_resolved=false` が残る場合はログ警告を出力し、当該フラグ状態を維持したまま処理継続（手動調査待ち）
- **出力スコープ**: 広域モードでは**広域 per-mesh CSV のみを新規出力**し（GeoJSON は出力しない）、merged 系ファイルへの差分書き換えは行わない。merged.csv の更新は FR-008 の再実行に委ねる。通常 per-mesh ファイル（`<meshcode>.csv` 等）も**更新しない**
- **広域 per-mesh ファイル命名**: 解析識別子 `<N>-<対象メッシュコード>-<コーナー>` を基底とした命名（例: `4-5239-NW.csv`）を採用し、同一ディレクトリ `$DATA_DIR/results/csv/` に置く。通常 per-mesh（`3-<meshcode>.csv`）とプレフィックスで機械的に区別できる

**解析ウィンドウ決定: 4 コーナー配置パターン探索（2026-06-02 改訂・FR-014 内部処理として位置付け 2026-06-09）**

N×N ウィンドウ内での対象メッシュの位置を **4 つのコーナー**（NW/NE/SW/SE。対象メッシュを置く隅を表し、ウィンドウは対角方向に展開する）に限定し、
最大 4 パターンを順に試して、対象メッシュ所属の全対象ピークが `key_col_resolved=true` になった時点で早期終了する。本制御は FR-014 内部のオーケストレーション処理として実行される。
すべて失敗した場合に次の N（4→5→6）へエスカレーション（FR-022 が制御）。
同一メッシュに複数の対象ピークが所属する場合は、所属メッシュ単位にグルーピングして一括解析する（同一ウィンドウの重複解析・出力ファイル名の衝突を防ぐ）。

例: 対象メッシュ = 5135（八経ヶ岳）、4×4 の場合

```text
配置（対象メッシュを置く隅）    探索方向           ウィンドウ範囲
NW（北西隅）                   南・東に広い        4835〜5138
NE（北東隅）                   南・西に広い        4832〜5135
SW（南西隅）                   北・東に広い        5135〜5438
SE（南東隅）                   北・西に広い        5132〜5435
```

（2026-06-12 訂正: 旧例示の NW/NE 行はウィンドウ範囲の計算が誤っており（対象メッシュがコーナーに位置しない範囲を記載）、コーナーの座標表記 (col, row) も SRS と不整合だったため、方角ベースの表記に統一して再計算した）

- ウィンドウ内の存在しないメッシュ（海上・日本国外。日本全土1次メッシュコードリスト基準）は NODATA 充填で解析を続行する（FR-004 のリスト外メッシュと同じ扱い）
- スキップするのは「ウィンドウ内の存在メッシュが**それまでに解析済みのどの範囲**（3×3 解析範囲および既解析の広域ウィンドウ）と比べても 1 枚も増えない配置」のみ（解析しても新情報が得られないため）。N=5 の配置が N=4 の配置と完全に重複するケースも含む
  - 2026-06-12 第1回改訂: 旧規則「存在しないメッシュを含むパターンはスキップ」では、海岸沿いの対象ピーク（鳥海山＝本 ADR の確定対象が日本海沿岸）でウィンドウがほぼ必ず海域メッシュを含み、全パターンスキップ＝広域解析が成立しなくなるため「新規存在メッシュゼロのパターンのみスキップ」に再定義した
  - 2026-06-12 第2回改訂: さらに一般化。「3×3 解析範囲から 1 枚も増えない」だと N=4 の配置と N=5 の配置が同じ範囲になるケースを見落とす可能性があるため、「それまでに解析済みのどの範囲と比べても増えない」に拡張した
- **4 コーナー方式の根拠**: 対象ピークから対角方向に最大 (N-1)√2 メッシュ離れたコル候補までカバーできる（中央配置の (N-1)/2 比で √2(N-1)/((N-1)/2) ≒ 2.8 倍の到達距離）。4 コーナー（NW/NE/SW/SE）の試行で全方位を覆える
- N² パターン全件探索（旧方式）と比較して試行回数を最大 N² → 4 に圧縮できる（N=6 なら 36 → 4）。全方位カバー性と到達距離は維持
- 旧方式（N² 全パターン探索）は Alternatives 参照
- 将来の最適化余地: C++ エンジンが `key_col_resolved=false` の際に「どの境界辺に接しているか」を出力すれば
  優先コーナーを絞れる（COD ステージで検討）

max pooling を選んだ理由: プロミネンス計算目的では山頂を保持する必要があり、
平均や最小値では山頂標高が過小評価される。Key コルは実際より高く評価される（プロミネンスが保守的方向に過小）が、
申請において保守的であることは許容範囲。

※ ADR-SRS-011（2026-05-21）により、`area_complete=false` のトリガー条件は廃止された。delete判定ゾーン 250m キャップにより AZ・delete判定ゾーンとも複数の 3×3 メッシュ統合段階で完結ポリゴンが見つかる想定となったため、FR-014 のトリガーは `key_col_resolved=false` のみで十分となった（詳細は ADR-SRS-011 副次効果「広域再解析のトリガー縮小」を参照）。

## Alternatives

| 案 | 却下理由・備考 |
|---|---|
| N² スライディングウィンドウ全パターン探索（旧方式・2026-06-02 廃止） | 対象メッシュ位置を (1,1)〜(N,N) の N² 通り全試行する案。4 コーナー（NW/NE/SW/SE）方式で全方位・遠距離カバーが達成できることが確認できたため、試行回数を N²→4 に圧縮。N=6 で 36 回が 4 回に減るメモリ・計算コスト削減を優先。 |
| average pooling | 山頂標高が過小評価される |
| 別途レベル 14 タイルを取得・保存 | ストレージ増加・prefetch 工数増。メモリ効率改善なし。 |
| `key_col_resolved=false` を無視して申請 | 誤ったプロミネンス値で申請することになる。不可。 |
| 8×8 メッシュを通常処理に採用 | 計算コストが 7 倍以上に増大。ほぼ全サミットに適用するのは非現実的。 |
| 6×6 + L14（当初案） | 解析半径 185 km・推定メモリ ~57 GB で 3×3/L15 と同等。対象 1〜2 件に対してオーバースペック。4×4+5×5 段階構成のほうがメモリ効率が良く対象ケースも十分カバーできる。 |
| Key Col 方向への矩形メッシュ拡張 | 鳥海山のように N-S 方向だけ延ばす 4×2 等の矩形解析。8 タイルで済み level-14 より解像度を保てる。ただし MeshSet の非正方形対応と拡張方向の自動判定が必要。対象が 1〜2 件であるため実装コスト対効果の面から不採用。 |
| `area_complete=false` をトリガーに追加（ADR-SRS-011 以前の旧設計） | AZ が解析境界で途切れたまま FR-009 に渡ると point-in-polygon 突合が失敗するリスクを懸念して追加していた。ADR-SRS-011（2026-05-21）で delete判定ゾーン 250m キャップが確定したことにより廃止。AZ・delete判定ゾーンはいずれも複数の 3×3 メッシュ統合段階で完結ポリゴンが見つかる想定となったため、`area_complete=false` が想定外に発生した場合は merge.py の `is_area_incomplete` 不備フラグで処理停止する設計に変更（ADR-SRS-011 参照）。 |
| per-mesh フェーズ2 内配置（2026-05-16 暫定設計） | per-mesh CSV の `key_col_resolved=false` を直接トリガとする案。同一ピークが複数の per-mesh 解析に出現し、別解析では `key_col_resolved=true` となる可能性がある。per-mesh 段階で確定的に判定できないため、フェーズ3 統合で本来 confirmed になるピークまで広域再解析する無駄が生じる。SRS FR-018 とも循環参照を生んだ。フェーズ3.5 配置に修正。 |
| フェーズ3 末尾の単発処理 + merged 差分上書き（2026-05-18 午後の暫定） | FR-014 を「merged.csv / merged_peak.geojson を入力に取り、該当レコード・ポリゴンを差分上書きする独立処理」と位置付ける案。ユーザーが意図していた「per-mesh エンジン（FR-004）を広域モードで再呼び出しし、FR-008/FR-018 を再実行して merged を再生成する縮小版パイプライン」とは構造が異なり、merged を破壊的に書き換える点が問題。広域 per-mesh ファイル群を新規生成し FR-008/FR-018 のループに乗せる縮小版パイプライン方式（本決定）に修正。 |
| FR-014 スタブ化 + FR-004 N≥4 モード集約（2026-06-02 採用 → 2026-06-09 廃止） | FR-014 を独立実装を持たないスタブとし、4 コーナー生成・対象ピーク絞り込み・早期終了等のオーケストレーション責務を FR-004（N≥4 モード）に集約する案。実装観点では C++ エンジンを単一の入口で呼び出せるため簡潔だったが、SRS 表現上 FR-004 が「3×3 通常モード」と「広域モード」の 2 つの責務を同居させることになり、FR-005 から見た上位制御の所在が一意に定まらない問題が FR-005 レビュー（観点 L）の整理で顕在化。SRS の責務分離を優先し、FR-014 を「広域結合解析オーケストレーション」として独立した実装本体に格上げする本決定に修正（実装側の C++ エンジン共有原則は維持。`findsummits` のオプションフラグ／別バイナリ等の実装選択肢は Consequences §6 を参照）。 |

## Consequences

1. **座標変換（L15→L14）**: タイル単位 max pooling を採用（確定）
   - 各 256×256 L15 タイルを 128×128 L14 タイルに 2×2 max pooling
   - combined image を L15 で先に構築してから pooling するのではなく、**タイル読み込み時に pooling して
     L14 combined image（4×4 で ~46k×38k px ≈ 7 GB float）に直接書き込む**
   - 理由: 4×4 の L15 combined image は ~28 GB になり実用不可
   - NODATA (-9999.0f) は max 計算で自然に正しく扱われる（実標高があれば実標高が残る）
   - **ピーク座標は L15 座標を維持**（2026-06-12 明記）: max pooling では 2×2 のうち採用した最大値ピクセルの
     L15 座標を保持し、ピーク座標は L15 相当の座標で CSV 出力する（pooling は標高値の縮約であり座標の縮約ではない）。
     これにより FR-007 の対象ピーク絞り込み・FR-008 の同一ピーク判定（L15 タイル座標一致）が通常 per-mesh と同一基準で機能する
   - **max pooling 同値時の採用ピクセル決定**: 2×2 の複数ピクセルが同一標高最大値を持つ場合、採用するピクセルの
     決定規則は実装で決定的（同じ入力に対して常に同一の L15 座標を返す）とすること。具体的な優先順位規則（例: 北西優先等）は HLD/LLD ステージで定義する
   - 実装: `load_mesh_tile` に `zoom_level` 引数を追加。combined image サイズと配置オフセットを
     `zoom_factor`（L15=1, L14=2）で割る

2. **col_margin_px**: px 単位のまま出力、zoom_level 列を CSV に追加して merge.py 側で補正（確定）
   - L14 の 1 px = L15 の 2 px 相当（地理的 2 倍幅）
   - `key_col_resolved` の判定ロジックは変更なし（真偽値方向のみ反転: コルが確定済みなら true）
   - stability 判定時は `col_margin_px × zoom_factor` で L15 相当値に換算（merge.py 側で実装）

3. **1px ボーダー**: L14 でも現行実装を踏襲、許容する（確定）
   - L14 の 1 px ≈ 20m（L15 の 2 倍幅）だが、広域モード対象ピーク（鳥海山・八経ヶ岳）は
     解析範囲中央付近に位置するため影響はない
   - `load_mesh_tile` の calloc 初期化 + 1px オフセット配置は変更なし

4. **257×257 オーバーラップ**: 広域モード（FR-014）では使用しない（確定）
   - `load_mesh_tile` が使う `elev_load_tile_into_big` はタイル本体 256×256 のみ読む
   - cross-tile pooling（境界をまたぐ 2×2 group）は実施しない
   - 隣接タイル境界での ~10m 格子誤差はプロミネンス 150m 判定に対して無視できる

5. **merged 系ファイルの更新方法**: 広域モード（FR-014）は merged.csv を**直接書き換えない**。
   広域モードで `findsummits`（[ADR-SRS-010](ADR-SRS-010-cpp-opencv-migration.md) 移行後の C++ エンジン）が
   per-mesh CSV を新規出力し、それを通常 per-mesh ファイル群と一緒に FR-008 に再投入する
   ことで merged.csv が再生成される（広域モードは GeoJSON を生成しないため merged_peak.geojson は再生成しない）。
   **FR-014 の責務**は「対象ピークの所属メッシュ単位グルーピング → 4 コーナーパターン生成 → 広域モード解析（FR-015 + FR-005/FR-006/FR-007 パイプライン）→ 対象ピーク行のみ広域 per-mesh CSV 出力 → 対象メッシュ所属の全ピーク `key_col_resolved=true` で早期終了」（単一 N での処理）。
   FR-008 の再実行・N エスカレーション判定（N=4→5→6）・フェーズ4 移行判断はコル充足判定（FR-022）が担う。
   FR-004 は 3×3 通常モード専用に純化されており、広域モードには関与しない。

6. **実装原則: per-mesh エンジン（C++）の拡張・再利用（ロジック重複禁止）**
   広域解析（FR-014）は per-mesh 解析エンジン（[ADR-SRS-010](ADR-SRS-010-cpp-opencv-migration.md) 移行後の `findsummits` C++ 実装）を拡張して対応し、
   ピーク検出・コル検出・Union-Find・アクティベーションゾーン計算のロジックを Python 側で再実装してはならない。
   既存 C++ モジュール（`mesh`, `elevation`, `unionfind`, `analyze`, `mesh_analyze`, `activation`）を
   すべて共有し、以下の 2 点を C++ エンジンに追加するのが正しいアプローチ:
   - **処理モードパラメータ（メッシュ数 N + ズームレベル L）**: 通常モード（N=3, L=15、現行動作）に加え、
     広域モード（N=4/5/6, L=14）を入力で切り替え可能にする。
     L=14 のときはタイル結合時に 2×2→1px max pooling でダウンサンプルし、ファイル出力名は広域用に変える。
   - **対象ピーク座標リスト入力 + 4 コーナーパターン生成**: 広域モード時に対象ピーク座標リストを受け取り、所属メッシュ単位にグルーピングした上で、各対象メッシュについて 4 コーナー（NW/NE/SW/SE）配置の N×N メッシュコードリストを内部生成して順次解析する。対象メッシュ所属の全ピーク `key_col_resolved=true` で早期終了。対象ピーク行のみを per-mesh CSV に出力。

   SRS 上の責務配置:
   - **FR-004（3×3 メッシュ結合解析オーケストレーション）**: 通常モード（N=3, L=15）固定での per-mesh パイプライン制御。広域モードには関与しない
   - **FR-014（広域結合解析オーケストレーション）**: 広域モード（N=4/5/6, L=14）の制御。所属メッシュ単位グルーピング・4 コーナーパターン生成・対象ピーク絞り込み・早期終了を内部処理として実行
   - **FR-015（標高地形図出力）・FR-005/FR-006/FR-007（per-mesh パイプライン）**: FR-004 と FR-014 の両方から呼び出される共通サブ処理（FR-015 は広域でも出力し、解析範囲の目視確認を可能にする）
   - **FR-022（コル充足判定）**:
     - `merged_peak.csv` から `key_col_resolved=false` の対象ピーク座標を抽出
     - 陸地最高峰リスト一致ピークを広域対象から除外し、`key_col_resolved=true`（Key コル=海面 0m）に更新（[ADR-SRS-019](ADR-SRS-019-land-summit-highest-peak-handling.md) 参照）
     - 残った未確定ピークを `key_col_unresolved_peaks-<N>.csv` として出力し、次段の N+1 と共に FR-014 へ渡す（エスカレーションループ）
     - 各 N 試行後に FR-008 を再実行して `merged_peak.csv` を再生成し、未確定ピークが残るかを再判定
     - 全充足ならフェーズ4 へ、N=6 でも未充足ならそのままフェーズ4 へ（FR-009 の `is_key_col_unresolved` 不備フラグで異常終了）

   標高解析ロジック・4 コーナー生成は C++ エンジン側に留める。

   COD ステージでの実装選択肢（どちらも可）:
   - `findsummits` のオプションフラグとして追加（例: `--zoom=14 --target-peaks=<csv>`）
   - 別バイナリ（例: `findsummits_extended`）として C++ モジュールを共有リンク
